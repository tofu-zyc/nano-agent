# 下一个大版本：v0.3 – v0.6

日期：2026-10-23。来源：和用户讨论的“下一个大版本”方案（9 项需求和用户的反馈）。
分 12 个阶段，每个阶段 `make test` 全过后单独提交，并更新 docs/HANDOFF.md；按下面的版本划分打 tag 发布。
**大版本在自己的分支上做（v0.3 是 `dev/v0.3`），不直接改 main**，见文末「分支」。

## 用户的原则（先读，后面的取舍都以这里为准）

1. **安全靠人，不靠工具强加限制。** 权限规则不变：工作目录读写，外面只读，写外面要提权审批。新能力（定时任务、computer use、MCP）沿用会话的权限模式，不另加黑名单。
2. **少内置机制。** 网关只提供简单、可组合的能力：文件、工具、技能、定时。“怎么整理记忆”这类策略写在可以改的技能文件里，不写死在 Go 代码里，复杂的玩法交给用户自己。
3. **agent 是一直在的个体，不是临时工具。** 不做 subagent 那种“临时开一个 agent 干完就扔”的工具。agent 之间像同事一样聊天。
4. **群聊像真人。** 不展示思考和工具过程，不长篇大论，不是每句都回，只能用少量指定的工具。干活的样子和群聊的样子是两回事。
5. **缓存优先。** 系统提示、工具定义只在固定时机变：新会话、`/reset`、压缩之后。其他时候请求前缀逐字节不变。
6. **所有文件放在 `~/.nano-agent`。** 密钥加密存储（`enc:v1:`），网页只回传“有没有设置”。

## 阶段 1：上下文计量和 `/context`（v0.3）

现在用“字节数 ÷ 3”估算 token，不准，也没有用接口返回的真实用量。阶段 1 和 2 都基于这里的计量。

- 每次模型请求结束，把接口返回的 `prompt_tokens`、`cached_tokens`，以及当时的历史位置（绝对下标），记进会话设置（settings.json）。重启后还在。
- 当前上下文 = 上次真实的 `prompt_tokens` + 之后新增消息的估算。从没请求过的会话全部按估算算。
- 窗口大小用这个会话所用模型的 `context_window`（models.json）。
- 分项（人格、工具定义、摘要、对话、对话里的工具结果）先各自估算，再按“真实总数 ÷ 估算总数”等比缩放，让分项加起来等于真实总数。
- `/context` 输出示例：
  ```
  上下文 41.2k / 128k（32%）· deepseek-v4-flash
    人格 1.1k · 工具定义 3.4k · 摘要 2.0k（14:02 整理掉 86 条）
    对话 34.7k（52 条，工具结果占 21.3k）
  上次请求：输入 41.2k（缓存命中 94%）· 输出 1.3k
  到 96k（75%）时自动整理；空闲 30 分钟后整理；/compact 现在整理
  ```
- 网页会话面板加一条上下文进度条，内容同上。`Gateway` 工具的会话信息里也带上这些数字。
- 命令表（`app.Commands`）加 `context`，所有人可用。
- 测试：真实用量 + 估算的组合；分项缩放后的总和；没请求过的会话；换模型后窗口跟着变。

## 阶段 2：上下文压缩（只动上下文，不动记忆）（v0.3）

现在的问题：
- 摘要时把要丢的整段历史（含工具输出原文）一次性塞给模型。段太长时摘要请求自己就超限，失败后只能“省略旧对话”。
- 只有一个阈值，到了才同步压缩，用户要干等。
- 大块的工具结果一直原样占着上下文。

### 设置（schema 驱动，设置页能改；每个 agent 可以覆盖，阶段 6 起）

- `context.compact_at`：上下文到窗口的多少时自动压缩，默认 `0.75`。
- `context.compact_to`：压缩后目标占比，默认 `0.4`。
- `context.keep_turns`：最近几轮原样保留，默认 `4`。
- `context.idle_compact`：空闲多久后自动压缩，默认 `"30m"`，`"0"` 关闭。
- `context.idle_compact_min`：空闲压缩只在上下文超过窗口的多少时才做，默认 `0.3`。
- `context.archive_days`：`/reset` 归档的历史留几天，默认 `90`，`0` 永久保留。
- 旧的 `llm.max_history_tokens`：用户显式设过的，继续当作绝对上限。

### 压缩怎么做

1. **第一层，不调模型。** 保留区以外、超过 2KB 的工具结果换成占位，比如：
   ```
   [已省略：Read a.go 的输出，12KB。需要时重新读取]
   ```
   调用本身保留。原始历史文件不改：在会话设置里记一张“被省略的消息下标 → 占位文字”的表，组请求时套用。
2. **第二层，摘要。** 把要整理掉的那段按“摘要模型窗口的 1/3”切块，按顺序滚动：`摘要ᵢ = 总结(摘要ᵢ₋₁, 块ᵢ)`。块里每条工具输出最多保留 2KB。这样多长都能压。
   摘要用固定结构：
   - 用户的目标；
   - 做过的决定；
   - 涉及的机器、目录、文件；
   - 没做完的事；
   - 用户的偏好；
   - 关键数据和结论。
   上一次的摘要作为 `摘要₀` 滚进来。
3. 最近 `keep_turns` 轮和当前这一轮永远原样保留。只在用户消息处切，不拆开工具调用和它的结果（沿用 `CutPoint` 的规则）。
4. 摘要失败时：只做第一层；还超限才退回现在的“省略”。当前这一轮绝不丢。

### 什么时候压缩

- **请求前（同步）**：上下文超过 `compact_at` 时，先压缩再请求。现在就是这样，但换成上面的新做法。
- **一轮结束后（后台）**：超过 `compact_at × 0.8` 就趁空闲在后台压缩，下一条消息就不用等。压缩进行中来了新消息，就排队等它做完；网页和聊天里显示“正在整理上下文…”。
- **空闲（后台）**：会话空闲超过 `idle_compact`、并且上下文超过 `idle_compact_min`，压缩一次。每段空闲只做一次。
- **手动**：`/compact [要特别保留的重点]`（管理员）。重点文字交给摘要模型。
- 压缩完在聊天里给一句：“已整理上下文：96k → 41k”。简洁档只在网页显示。
- 压缩**从不**改知识库。整理记忆是阶段 10 的事，命令也分开：`/compact` 只压上下文，`/sleep` 才整理记忆。

### `/reset` 改成归档

- `/reset` 不再删历史文件，而是挪到 `data/archive/<会话ID>/<时间>.jsonl`。阶段 10 做梦时要读这些“日记”。
- 网关每天按 `archive_days` 清理一次过期归档。

### 删除会话历史

用户觉得某段对话没营养，可以直接删，删了就是真删：不留归档、不进梦里。

- **整段删**：
  - `/reset 删除`（管理员）：清空当前上下文，不归档，历史文件直接删掉；
  - 网页会话设置里“删除全部历史”：当前历史连同这个会话的所有归档一起删，要二次确认。
- **删其中几轮**：网页会话里可以选中一轮或连续几轮对话（用户消息连同它后面的回复、工具调用一起）删除。
  - 实现：重写这个会话的历史文件（写临时文件再改名）。被省略消息的下标表、`Base`、阶段 1 记下的计量位置，都要跟着重算。
  - 删的是摘要已经整理过的部分时，摘要里可能还留着概要。界面上提示一下，并给一个“清空摘要”按钮。
  - 删除改变了请求前缀，下一次请求缓存不命中，这是预期的。
- **删归档**：网页上列出这个会话的归档（时间、条数），可以单独删。
- **和做梦的关系**：删掉的内容从 `dream-state.json` 的进度里去掉，以后不会再被读到。已经整理进知识库的条目不自动删，条目上有 `source`，用户可以到知识库页按来源找出来删。
- `GatewayAdmin` 加 `history_delete`（整段或按轮），任何模式都审批，方便用户在聊天里说“把刚才那段删了”。
- 已有的 `/undo` 不变，仍然只撤回最近一条。

### 测试

- 用 mock 模型回放长对话：
  - 到阈值自动压缩，压缩后不超过目标；
  - 要整理的段落超过摘要模型窗口时能分块完成；
  - 工具结果占位生效，原始历史文件逐字节不变；
  - 当前这一轮保留；
  - 摘要失败时退回第一层。
- 用假时钟测空闲压缩；测 `/compact` 带重点。
- 两次压缩之间，相邻两次请求的消息前缀完全相同（缓存）。
- `/reset` 后能在 archive 里找到旧历史；过期归档会被清理。
- `/reset 删除` 不留归档；网页删除全部历史连归档一起删。
- 删中间几轮后，历史文件、`Base`、被省略消息的下标表、计量位置都正确，下一次请求的消息里没有被删的内容。
- 删除的内容不再出现在 `Diary` 里。

## 阶段 3：聊天里的显示档位（v0.3）

- 三档：
  - `详细`：思考、工具、正文都显示；
  - `过程`：显示工具，不显示思考；
  - `简洁`：只显示正文，处理中只有一行状态，比如“正在执行 Shell…”，结束后删掉状态只留答案。
- 设置分三层：
  1. 全局默认 `channels.show`，默认 `过程`；
  2. 每个机器人覆盖（阶段 6 前是 `telegram.show`、`feishu.show`）；
  3. 每个窗口覆盖：`/show 详细|过程|简洁`，记在 endpoints.json。
- 网页永远显示全部。终端（cli）也吃这个设置。
- 群聊（阶段 7）不受这个设置管，固定是“静默”：不发任何过程，只发“正在输入”状态。
- 实现：在 `channel.RunView` 外面包一层，按档位过滤 `Reasoning`、`Tool`、`ToolResult`、`Note`。
- 只影响显示。思考要不要回传给模型，还是由 `llm.send_reasoning` 管。
- 测试：假渠道在三档下收到的内容。

## 阶段 4：网络搜索（DeepSeek 官方接口）（v0.3）

接口文档：https://api-docs.deepseek.com/zh-cn/guides/search/ 。用法如下：
- **Search**：`POST https://api.deepseek.com/v1/tools/search`
  - 参数：`query`（1–128 字，支持 `site:`、`lang:`、`after:` 等运算符）、`count`（1–50，默认 10）、`need_content`。
  - 返回 `results[]`，每条有 `title`、`url`、`summary`（600–800 字，给模型用）、`date`、`site_name`、`authority`、`rerank_score`。
- **Fetch**：`POST https://api.deepseek.com/v1/tools/fetch`，参数 `url`，返回 `title` 和 Markdown 格式的 `content`。
- **鉴权**：`Authorization: Bearer <DeepSeek API key>`。
- **价格**：各 5 元/千次成功请求，空结果和失败不计费。
- **限流**：Search 100 QPS，Fetch 25 QPS（另有按目标域名的限制）。
- **错误码**：400、401、402（余额不足）、403、404（抓不到内容）、408、413、429、5xx。408、429、5xx 可以等一会儿重试。

### 实现

- 新包 `internal/search`：`Provider` 接口（`Search`、`Fetch`），先只实现 `deepseek`。
- 两个由网关执行的工具（和 `Gateway`、`Skill` 一样不经过内核）：
  - `WebSearch {query, count}`：`count` 默认 6，最多 10。输出紧凑文本：`[1] 标题 — 链接（日期 · 站点）` 加一段 summary。
  - `WebFetch {url, offset}`：Markdown 每次最多 20000 字。超过的部分提示“还有 N 字，用 offset=… 继续读”。
- 设置 `[search]`：
  - `enabled`，默认 true；
  - `provider = "deepseek"`；
  - `api_key`（secret）：留空时，用 models.json 里 base_url 主机是 `api.deepseek.com` 的那个接口的 key；
  - `count`。
- 没有可用的 key 时，不提供这两个工具。
- 只读，任何权限模式都能用，访客也能用。
- 工具说明里要求模型回答时附上来源链接。
- 401、402、429 给中文的明确提示。成功次数计入 `/status` 的当天统计。
- 测试：httptest 假接口；输出格式；key 回退；各种错误；Fetch 分页。

## 阶段 5：定时任务（v0.3）

- `data/schedules.json`，每个任务有：
  - `id`、`name`；
  - `when`：cron 五段式、`every 30m`、`at 2026-10-24 08:00` 三种写法，时区用网关所在时区；
  - `agent`：阶段 6 前固定为默认 agent；
  - `prompt`：要做什么；
  - `deliver`：结果发到哪里，可以是一个或几个窗口，阶段 8 起也可以是内部群；
  - `workspaces`、`mode`：不能高于创建者会话的模式；
  - `enabled`、`created_by`；
  - `last {at, ok, summary}`；
  - `catch_up`：错过了要不要补跑，默认补跑一次。
- cron 解析可以用 `github.com/robfig/cron/v3` 的解析器，也可以自己写一个小的。夏令时要测。
- **执行**：
  - 每个任务有自己的会话 `cron:<id>`。每次运行前先 `/reset`（归档），所以每次都是全新上下文，不污染别的会话。
  - 最终回复发到 `deliver` 的窗口，开头写 `[定时任务 早报]`。
  - 有超时（默认 30 分钟），失败也通知。
  - 运行中要审批时，审批请求发到 `deliver` 的窗口；30 分钟没人管就拒绝。
- **错过的任务**：网关停机期间到点的，启动后 1 小时内补跑一次；超过 1 小时只记录“错过”。
- **`Schedule` 工具**（管理员会话）：`create`、`list`、`update`、`delete`、`run_now`。
  - 新增、修改、删除按会话的权限模式走：审批模式要审批，自动模式直接做。
  - 用户说“每天 8 点给我发 AI 新闻”，模型就调它，结果发到当前窗口。
  - 阶段 6 起，可以把任务交给别的 agent 去干。
- **命令**：`/cron` 列出；`/cron run|on|off|rm <编号>`。
- **网页**：“定时任务”页，能看下次运行时间、最近几次结果，能立即运行、编辑、开关。
- **测试**：解析和下次运行时间（含时区、夏令时）；补跑；mock 模型执行并投递；审批模式下的审批；超时。

## 阶段 6：agent 和机器人绑定（v0.4）

**agent** 是一个一直在的个体，配置存在 `data/agents.json`：
- 名字、头像（一个 emoji）；
- 模型、思考强度；
- 默认工作目录、默认权限模式；
- 工具白名单：分“干活”（默认全部）和“群聊”（默认 `WebSearch`、`Knowledge` 只读）两套；
- 群聊行为（阶段 7）；
- 压缩、做梦的设置覆盖。

人格在 `agents/<agent>/persona.md`。

### 迁移（不能丢东西）

- 建默认 agent，id 为 `default`，名字取“小纳”。用户可以改名。
- `personas/default.md` 挪到 `agents/default/persona.md`；`personas/` 里只留会话专属的覆盖。
- 现有的会话、窗口、Telegram 和飞书配置全部归默认 agent。

### 会话 ID

- 默认 agent 的会话 ID 不变（`main`、`tg:123`……），这样不用迁移历史。
- 其他 agent 加前缀：`@<agent>/main`、`@<agent>/tg.<bot>:123`。
- 会话设置里记 `agent`。
- 人格查找顺序：`personas/<会话ID>.md` → `agents/<agent>/persona.md`。

### 机器人实例

- `data/bots.json`，每个机器人有：`id`、`kind`（telegram / feishu）、`name`、凭据（加密）、代理、`agent`、`show`。
- 一个机器人只绑一个 agent；不绑机器人的 agent 只能在网页和内部群聊里说话。
- 旧的 `[telegram]` 和 `[feishu]` 配置当作 id 分别为 `tg`、`feishu` 的两个机器人，绑默认 agent。渠道名、窗口 key 保持不变，不迁移历史。
- 新机器人的渠道名是 `tg.<bot>` 或 `feishu.<bot>`。
- **身份**：
  - Telegram 的用户 ID 全局唯一，不同机器人看到的是同一个人，管理员配置照常生效。
  - 飞书的 open_id 每个应用不一样，要用 union_id（或 user_id）认人。管理员列表里写飞书身份时要能对上多个应用。

### 界面和命令

- **网页**：
  - “agent”页：增删改；人格编辑可以套用自带人格（小纳、大肥鱼）；模型、工具白名单、群聊行为等设置。
  - 拓扑里 agent 是一类节点：agent → 机器人 → 窗口。
  - 会话列表标上属于哪个 agent。
- **`/agent`**：显示你在和哪个 agent 说话。不提供切换，换 agent 就是换个机器人聊。
- **`Gateway` 工具**能查 agent 列表；`GatewayAdmin` 能建 agent、改设置、绑定机器人（审批）。

### 测试

- 迁移前后，会话、窗口、人格、历史都不变。
- 两个机器人分别路由到两个 agent。
- 每个 agent 用自己的人格和模型。
- 工具白名单生效。
- 飞书身份对应。

## 阶段 7：群聊行为（外部群）（v0.4）

去掉现在的“暂时只支持私聊”。每个群在每个 agent 下有一个会话。群里说话的人按访客权限处理；管理员在群里也能用命令，但工具只有群聊白名单里的那些。群会话默认不挂工作目录，管理员可以在网页上给某个群挂。

### 什么时候说话

- 群里每条消息都记进群会话的历史，格式 `[时间][昵称] 内容`，**不触发模型**，只是“听着”。
- **一定回**：被 @、有人回复这个机器人的消息、消息里叫了 agent 的名字。等 2 秒，把紧接着的几条一起处理。
- **可能插话**：群里安静 20 秒（可配置）以后，如果有新消息并且插话额度允许，就调一次模型。模型可以只回 `[不回复]`，表示这次不说话，网关看到就什么也不发。
- 插话积极度：`off` / `低` / `中` / `高`，对应每小时最多 0 / 2 / 6 / 15 次主动发言，两次之间有最短间隔。

### 怎么说话

- 群会话的系统提示 = 人格 + 群聊守则（`agents/<agent>/group.md`，没有就用内置的）。守则包括：
  - 口语、简短，一般一两句；
  - 不用标题和列表；
  - 不提工具和执行过程；
  - 不知道就不插话；
  - 用 `[不回复]` 表示沉默。

  内容对这个群会话保持不变（缓存）。
- 回复长度有硬上限，默认 300 字。超过就在合适的地方截断，并附一句“细节私聊我”。
- 像人一样发：按空行拆成最多 3 条消息，中间按长度停一会儿（最多 3 秒），生成期间显示“正在输入”。
- 不发任何思考、工具过程和用量说明。

### 前提条件（写进 doctor 和设置页提示）

- **Telegram**：要在 BotFather 里关掉机器人的 privacy mode（或者让机器人当群管理员），才收得到群里所有消息。
- **飞书**：要开“获取群组中所有消息”权限。

### 同一个外部群里有好几个机器人

- 机器人之间能不能看到对方的消息，是 Telegram、飞书平台的事，网关不替平台转告。
- 平台推过来的其他机器人的消息，当作普通群消息处理，发言人标上“（机器人）”；连续上限、频率这些防刷屏规则和阶段 8 一样生效，防止几个机器人在群里聊个不停。
- 推荐的做法还是阶段 8 的网关内部群，不用为每个 agent 占一个机器人名额。但用户愿意给每个 agent 绑一个机器人、拉进同一个群里玩，也支持。

### 其他

- 群会话的压缩阈值单独设，默认 `compact_at = 0.5`（群消息多，信息密度低）。
- 测试：
  - 被 @ 必回；
  - 没被 @ 时，在安静期之前不调模型；
  - `[不回复]` 时什么都不发；
  - 每小时上限和最短间隔；
  - 长度上限和拆条；
  - 工具白名单；
  - 平台推来的其他机器人的消息按普通群消息处理，防刷屏规则对它们也生效；
  - 没有任何过程消息。

## 阶段 8：网关内部群聊、agent 之间私聊（v0.4）

像“公司内部群”：用户在网页上建群，选哪些 agent 加入；agent 在群里说的话同步给群里所有成员。两个 agent 之间也可以私聊。

### 数据

- `data/rooms.json`，每个群有：`id`、`name`、成员（agent，以及用户本人，用户在网页上发言）、模式（`点名` / `自由`）、各种上限、是否暂停。
- `data/rooms/<id>.jsonl`：共享的群聊记录，只追加。

### 实现

- 内部群做成网关内部的一个渠道（`room`）。
- 每个成员 agent 在每个群里有一个会话：`room:<id>`，非默认 agent 是 `@<agent>/room:<id>`。群里的新消息作为 `[发言人] 内容` 进入每个成员的会话。
- 直接复用阶段 7 的群聊引擎：什么时候说话、怎么说话、静默规则都一样。
- 两个 agent 的私聊 = 只有这两个成员的内部群，第一次发消息时自动建立。

### agent 主动发消息：`Message` 工具

- 参数：`{to: "room:<群名>" | "agent:<名字>", text, wait}`，干活的会话和群会话都能用。
- 消息投进对应的群，对方在它自己的群会话里看到并按规则回复。
- `wait: true`（默认 false）时，等对方在这个群里的下一条回复，最多 5 分钟，作为工具结果返回。就像给同事发消息然后等他回，对方还是那个一直在的 agent，不是临时开出来的。
- 回复也照常留在群里。

### 防止乱成一锅粥

- **点名模式（默认）**：agent 只在被 @（被人或别的 agent）或者私聊时说话。
- **自由模式**：按插话积极度插话；对 agent 发来的消息，插话概率再降一档。
- **连续上限**：群里连续 8 条（可配置）都是 agent 发的、中间没有人说话，就自动暂停，网页上显示“讨论已暂停，等你发言”。人一说话就恢复。
- **频率**：每个 agent 在每个群里有最短发言间隔（默认 10 秒）和每小时上限。
- **乒乓检测**：两个 agent 来回超过 6 轮、都没有提到新的人，就暂停。
- **预算**：每个群每天的 token 预算，用完暂停。
- **手动**：网页上能暂停、恢复群，禁言某个 agent；`/room pause|resume`。

### 网页和测试

- **网页**：内部群聊界面（多人头像、@ 补全），群列表，成员管理；拓扑里显示 agent 之间的群。
- **测试**：
  - 消息扇出给所有成员；
  - 点名规则；
  - 连续上限暂停、人说话后恢复；
  - 频率和预算；
  - 乒乓检测；
  - `Message` 带 `wait` 等到回复、超时；
  - 私聊自动建立。

## 阶段 9：知识库（长期记忆）（v0.5）

### 存放

- 每个 agent 在 `agents/<agent>/knowledge/` 下有自己的知识，所有 agent 共用的放在 `knowledge/`。
- 一条一个 Markdown 文件，开头一段 frontmatter：
  - `title`；
  - `type`：事实 / 偏好 / 经验 / 流程 / 人物；
  - `tags`、`updated`、`source`：来自哪个会话或哪次做梦；
  - `visible`：`all` / `admin` / 某个人的身份。
- 用户可以直接打开文件看、改。

### 索引

`INDEX.md` 每条一行：`标题 — 一句话说明（文件名）`。网关在每次写入后重新生成，不用模型维护。

### 技能形式

- agent 自己的技能放在 `agents/<agent>/skills/<名字>/SKILL.md`，格式和现有技能一样。
- `Skill` 工具列出“全局技能 + 这个 agent 的技能”，同名时 agent 自己的优先。
- 经验、流程类的知识可以直接写成技能。

### `Knowledge` 工具（网关执行）

- 动作：`list`（看索引）、`search {query}`（标题和正文的关键词 / 正则搜索，返回最相关的几段）、`read {path}`、`write {path?, title, type, tags, body}`、`edit {path, old, new}`（和 Edit 一样精确替换）、`delete {path}`。
- `write`、`edit`、`delete` 也能操作 `skills/` 下的文件。
- 路径只能落在这个 agent 的 `knowledge/`、`skills/` 和共用的 `knowledge/` 里。改共用知识按会话的权限模式走。
- 群会话里只能 `list`、`search`、`read`，并且只看得到 `visible: all` 的条目。
- 用户说“记住……”时，模型调 `write`。
- 以后可以加向量检索，这一版不做。

### 放进提示词

- 会话在固定时机（新会话、`/reset`、压缩之后）把索引快照放进系统提示，放在人格后面，最多 2k token，超了就只放标题。
- 快照存在会话设置里，两次刷新之间逐字节不变（缓存）。

### 命令、网页、测试

- **命令**：`/memory` 看索引；`/memory 关键词` 搜索；`/forget <编号或标题>` 删除（管理员）。
- **网页**：每个 agent 的“知识库”页，能搜索、看、改、删，能看到每条从哪来。
- **测试**：
  - 增删改查；
  - 路径越界被拒；
  - 索引重建；
  - 提示词快照只在固定时机刷新；
  - 群会话里按 `visible` 过滤；
  - agent 技能覆盖全局技能。

## 阶段 10：睡觉和做梦（v0.5）

agent 空闲时“睡觉”，睡觉时“做梦”：读最近的对话记录（日记），把该记住的内化进知识库和技能，并清理重复、过时的条目。

“怎么整理”写在技能里：内置一个 `dream` 技能，用户可以改，也可以在 `agents/<agent>/skills/dream/` 放自己的版本。网关只负责触发、提供工具、记录进度。

### 日记

- 来源：这个 agent 所有会话的历史文件（压缩不删原始历史），加上 `data/archive/` 里的归档。
- 进度存在 `agents/<agent>/dream-state.json`，记录每个会话、每个归档处理到哪了。
- 用户删掉的历史（阶段 2「删除会话历史」）不会再出现在日记里。

### 什么时候睡

设置 `dream.when`，可以是：
- `idle`（默认）：这个 agent 所有会话都空闲超过 `dream.idle`（默认 2 小时），并且有足够多（默认 20 条消息以上）没处理的日记；
- `nightly`：每天 `dream.at`（默认 03:00）；
- `off`。

每天最多 `dream.max_per_day` 次，默认 1 次。也可以手动 `/sleep`（管理员）。

### 怎么做梦

- 在 `@<agent>/dream` 会话（默认 agent 是 `dream`）里跑一轮，每次都是全新上下文。
- 系统提示 = 人格 + `dream` 技能的内容。
- 工具：
  - `Diary`：
    - `list`：哪些会话有没处理的日记，各多少；
    - `read {sid, from, limit}`：读一段，工具输出截短；
    - `done {sid, upto}`：标记处理到哪了。
  - `Knowledge`：完整的增删改查。
- 做梦用的模型可以单独设（`dream.model`），方便用便宜的模型。

### 被叫醒

- 做梦期间这个 agent 收到消息：其他会话照常回复，不受影响；做梦这一轮在下一个工具调用的间隙停下。
- 下次睡觉从 `dream-state.json` 记的位置接着做。
- 这个行为可以配置为“做完再醒”。

### 结果

- 这一轮的最终回复存成梦境日志：`agents/<agent>/dreams/<日期>.md`。
- 可选：醒来后给管理员发一句“昨晚整理了 5 条记忆、改了 1 个技能”。
- agent 状态在网页和拓扑里显示“睡觉中 💤”。

### 和压缩的关系

- 两件事互不依赖：做梦读的是原始历史，不受压缩影响；压缩也从不动知识库。
- 命令分开：`/compact` 只压上下文，`/sleep` 只整理记忆。

### 测试

- 用假时钟测空闲触发和定时触发；
- 每天上限；
- `Diary` 的分段读取和进度标记；
- 被叫醒后停下、下次接着做；
- 从文件加载 `dream` 技能（用户版本优先）；
- 知识库的改动带 `source: dream <日期>`。

## 阶段 11：MCP 透传（v0.6）

MCP 服务可以挂在任何一台接入的电脑上，用来实现“computer use 在某台机器上做”。C 内核不懂 MCP，只透传一个 stdio 进程。

### 协议 v10（内核和网关）

| 方向 | 消息 |
|---|---|
| 网关 → 内核 | `pipe_open {id, argv, env, cwd}`、`pipe_write {id, data}`、`pipe_close {id}` |
| 内核 → 网关 | `pipe_data {id, data}`（一行一条，MCP 的 stdio 本来就是按行分的 JSON）、`pipe_closed {id, code, error}` |

- 单行上限 32MB，截图是 base64，会很大。
- 进程跟着内核退出，用沿用现有的进程组清理。
- hello 里加 `desktop: true/false`：这个内核是不是跑在有桌面的登录会话里。
  - Windows：交互会话；
  - macOS：GUI 会话；
  - Linux：有 `DISPLAY` 或 `WAYLAND_DISPLAY`。

### 网关

- `internal/mcp`：用官方 Go SDK（`github.com/modelcontextprotocol/go-sdk`）做 MCP 客户端。传输层有三种：
  - 经内核的透传；
  - 网关本机 stdio；
  - 远程 streamable HTTP。
- `data/mcp.json`，每个服务有：
  - `name`；
  - `machine`：内核名 / `gateway` / URL；
  - `command`、`args`、`env`：env 里的密钥加密；
  - `enabled`；
  - `tools`：允许 / 禁用的工具；
  - `agents`：给哪些 agent 用；
  - `approval`：`always` / `per_turn` / `never`。
- **工具暴露**：每个 MCP 工具展开成模型工具 `<服务>__<工具>`，用原本的参数 schema，顺序固定。
  - 只在会话的固定时机（新会话、`/reset`、压缩后）刷新工具列表。
  - 服务离线时工具还在，调用时返回“服务不在线”，不从列表里拿掉（缓存）。
- **生命周期**：第一次调用时启动；崩溃后自动重启（有退避）；空闲 10 分钟关掉。
- **图片结果**：OpenAI 兼容接口的 tool 消息不能带图。图片放进紧跟着的一条用户消息 `[系统] <工具> 返回的截图`，前提是模型能看图；不能看图的模型只给文字，说明“截图已省略（当前模型不能看图）”。
- **网页**：拓扑里每台机器下面显示挂着的 MCP 服务和状态；可以添加、编辑、测试（列出工具）。
- **测试**：
  - 假的 MCP 服务（Python 脚本）经内核透传，能列工具、调工具；
  - 崩溃后重启；
  - 图片结果的路由；
  - 离线时的调用；
  - 审批的三种设置。

## 阶段 12：computer use（v0.6）

主要用在 Windows 和 macOS；Linux 要有桌面环境才有意义。底层用 Cua Driver（https://github.com/trycua/cua ，MIT），自己不实现点击、截图：
- 它直接操作本机的原生应用和浏览器：点击、输入、滚动、读无障碍树、截图，还能后台操作、不抢鼠标；
- 对外提供 MCP；
- macOS、Windows 可用，Linux 是预发布。
- 旧的 cua-computer-server 和 cua-agent 已经停止维护，不要用。

### 开启流程

1. 在网页上选一台机器“开启 computer use”，界面给出这台机器所在系统的 Cua Driver 安装命令（它自己的安装脚本，不打包进我们的发布包）。
2. 装好后检测，然后在 mcp.json 里登记 `computer@<机器>`。

### 前提检查

- 内核 hello 里 `desktop` 必须为 true。
  - Windows：内核由“当前用户登录时”的任务计划启动，v0.2.2 已修好；
  - macOS：launchd 用户 agent 跑在 GUI 会话里，并且给 Cua Driver 授了辅助功能和录屏权限；
  - Linux：有 `DISPLAY` 或 `WAYLAND_DISPLAY`。
- 不满足时给出原因和修法。

### 使用

- 内置技能 `computer-use`，告诉模型：
  - 先用无障碍树找元素，必要时才截图；
  - 每步操作后核对结果；
  - 付款、发消息、删除这类不可撤回的操作前，先问用户。
- 审批默认 `per_turn`：审批模式下，每一轮第一次操作某台机器的桌面时问一次“这一轮要操作 <机器> 的桌面，允许吗？”；自动模式不问。
- 能看图、定位准的模型效果好；只能处理文字的模型（比如 DeepSeek 的文本模型）靠无障碍树也能做不少事。

### 测试

- 用假的 computer MCP 服务测审批和技能加载。
- 真机测试写成手动清单（Windows、macOS 各一份）：打开记事本输入文字、在浏览器里搜索、截图回传。

## 风险和待定

- 群聊插话和做梦都花 token：有每小时、每天的上限；做梦可以单独用便宜的模型。
- 飞书多应用的身份对应（union_id），要在真实的飞书上验证。
- Telegram 群的 privacy mode 是机器人级别的设置，网关改不了，只能提示用户去改。
- MCP Go SDK 的版本选一个发布超过两周的稳定版。
- 版本划分可以按用户意见调整。

## 分支

- `main` 是稳定分支：只放已经发布的版本和小修（v0.2.x 这种）。用户的机器都从 main 打的标签自动更新。
- 每个大版本一个开发分支，从 main 开出：v0.3 是 `dev/v0.3`，v0.4 做完 v0.3 后再从 main 开 `dev/v0.4`，依此类推。阶段的提交都推到开发分支上，CI 照样跑（`ci.yml` 包括 `dev/**`）。
- main 上有小修时，把 main 合并进开发分支（`git merge main`），不要 rebase 已经推上去的开发分支。
- 一个大版本做完：
  1. 开发分支上 `make test` 全过、CI 全绿；
  2. 用户同意后，合并回 main：`git checkout main && git merge --no-ff dev/v0.3`；
  3. main 上 CI 全绿后，在 main 上打标签发布。
- **只能在 main 上打发布标签**：`release.yml` 会检查标签指向的提交在不在 main 上，不在就拒绝发布。开发分支的提交一旦成了“最新版本”，所有网关和内核都会自动更新上去。
- 开发分支发布前不打任何 `v*` 标签。

## 实现时的规矩（和以前一样）

- 每个阶段：`make test` 全过 → 单独提交（推到开发分支）→ 更新 HANDOFF（做了什么、坑、测试）。
- 测试一律用临时 `NANO_HOME`、`HOME`、`USERPROFILE` 和 mock 模型；不启动用户真实的配置（飞书、Telegram、真实模型）。
- 不碰用户真实的 `~/.nano-agent`、`nano-gateway.service`，也不碰真实 Windows 的环境（任务计划、PATH、启动文件夹）。
- 提交前跑 `build/tools/gitleaks git --no-banner --staged .`，不提交密钥和 data/。
- 只推开发分支；合并回 main 要用户同意。不改写历史、不强推。
