# 设计原则与目标架构

本文是 nano-agent 的目标设计，也是评审新功能的依据：它定义概念、原则和检验标准，并标出每个概念的现状。已实现的行为以 [架构](ARCHITECTURE.md)、[运行时](RUNTIME.md) 和各专题文档为准；本文的现状标记与代码不符时，以代码为准并修正本文。

现状标记：**已有**，代码已实现；**部分**，有零件但缺关键规则；**未做**，只存在于本文。

## 1 定位

一个运行时，三种用法：

- **陪伴**：工具型或拟人型 agent 和主人长期相处，聊天、记事、按约定行动。
- **团队**：agent 进入团队群和代码仓库，接收问题反馈，建立工单，交给执行者修改项目，再把结果送回原来的对话。
- **剧场**：给多个 agent 设定角色，放进同一个场景，观察并记录它们的行为，用于实验和内容创作。

三种用法共用同一套概念和执行底座。差别写在配置和规则里，不各自另起一套系统。

## 2 原则

1. **用最少的人的注意力，换最多做完的事。** 每条消息、每个提问、每个设置和每个面板元素都要说明它换来了什么。agent 只在有人必须行动、或有结果可用时开口：确认一次，问一个具体问题，做完报一次。
2. **模型判断，代码记事实。** 任务分类、做法和结论由模型给出；阶段、预算、权限、证据和谁能做什么由代码从记录推出，不采信模型的自称。完成必须引用真实证据。
3. **先记录，再动作。** 改变状态的决定先可靠落盘，外部动作在提交之后执行。结果不明时先核实，不自动重放。
4. **安全只加不减。** 现有审批、沙箱和权限规则不放宽；新需求用显式开启的新模式满足。剧场的戏剧性来自规则起作用，不来自放宽规则。
5. **前缀缓存优先。** 系统提示和工具定义保持稳定，动态内容追加进消息。改变既有前缀字节就是缓存回归，必须同步更新 `prefixVer`。
6. **概念少，设置少。** 新需求优先成为已有概念的属性或一段提示词，不新增概念；一个默认值适合几乎所有人时，不做成设置。
7. **一切有界。** 队列、记录、缓存、并发和预算都有上限和保留策略；满了明确拒绝或暂停，不静默丢弃。
8. **进程少。** 模型循环由 C 内核控制，业务状态在 Go 网关，执行在节点；不为新能力增加常驻服务。

## 3 核心概念

六个概念和两个接口。新代码、文档和界面使用这些术语；发给人的消息用平常的说法。

### 3.1 角色（Actor）

一个 agent 在某个场景里的一个位置：agent 的人格、模型、工具与权限上限和预算，加上这个位置自己的会话和收件方式。陪主人聊天的人格、派活的前台、写代码的执行者、剧里的人物都是角色，区别只在提示词、工具和消息从哪里来。

- 每个角色有自己视角的会话。普通会话可以换执行 agent；内部会话（life、整理记忆、定时任务、内部群成员）和分支的执行身份固定。
- 可用的工具和权限取 agent 上限、场景允许范围和会话设置的交集。
- 场景可以给角色叠加角色提示词，不修改 agent 自己的人格。角色提示词在一个场景内保持不变，放在成员会话的系统前缀里，不破坏缓存。

现状：**部分**。agent 配置在 `data/agents.json`；各视角已有独立会话（`main`、`tg:<id>`、`@<agent>/room:<id>`、`@<agent>/life`、`cron:<id>`、`hook:<delivery_id>`、分支）。场景级角色提示词已有（2b：`[场景]`、`[你的角色]` 放在成员会话的系统前缀里）。

### 3.2 场景（Scene）

角色和人共处的空间。它规定：

- 成员和各自的角色；
- 可见性：谁能听到谁（公开、私下、旁白）；
- 发言规则：点名、自由、轮流或导演控制；
- 时钟：真实时间或按回合（由发言规则决定，见 13.3）；加速时钟等有了具体需求再加；
- 预算池和结束条件；
- 场内允许的工具和出口。

外部的私聊和群聊、网关内部的群都是场景。规则属于场景，不属于 agent：同一个 agent 在团队群和闲聊群里可以遵守不同的规则。

现状：**部分**。内部群（`rooms.Room`）已有成员、点名/自由两种模式、暂停、禁言、双人私聊和每日 token 预算。2b 起规则属于场景（`internal/scene`，存在群记录或外部群的会话设置里，`a.sceneOf` 取），agent 上的群聊设置是没单独设置时的默认值；防刷屏阈值、预算池、场内工具表、`observe` 档都在场景规则里。缺可见性（第 3 步的导演台之后再看）。

### 3.3 事件（Event）

一条不可变的事实：来源、发出者、所在场景与线程、时间、内容。消息、定时到点、Job 结束、文件变化、仓库评论、导演插入的剧情都是事件。

- **来源（Source）** 产生事件。它定义什么算事件、事件属于哪条线程、该回复到哪里。
- 同一个事件只受理一次。
- 等待某个条件成立属于来源，不让承诺自己睡着等。

现状：**部分**。可靠事件日志（`internal/eventlog`）已记录 `message.received`、run、工具、审批、Job、`file.changed` 和到期事件，Hook 订阅它们；但聊天消息启动 run 仍直接走 `OnMessage`，事件只是旁路。网页事件总线 `events.Bus` 只用于展示，可以丢失，不是这里说的事件。

### 3.4 承诺（Commitment）

跨轮次的一件事。每个承诺都写清工作契约（第 4 节），它的阶段由事实推出。约定（Agenda）、回访（FollowUp）、定时任务（Schedule）、Hook、分支，以及以后的工单和角色的秘密目标，都是承诺的不同种类。

- 各种承诺共用契约字段和阶段推导，但仍是各自独立的对象，保留自己的到期、补跑、取消和验收规则；不合并成一个大任务对象。
- 阶段由一个纯函数从记录推出，表格从上往下第一行命中，每一行都有测试。
- 没有证据或放弃理由，承诺不能结束。

现状：**部分**。Agenda 已有完成条件、检查点和工具回执验收；Hook 和 Job 登记时固定来源、创建者、权限上限和工作目录；分支有宿主生成的最近进展。缺共用契约、阶段函数、结构化汇报，以及"等我处理"的汇总视图。

### 3.5 规则（Policy）

规则决定：哪些事件能变成承诺（准入）、谁能对谁说话、能用什么工具、能花多少预算、主动行为是执行还是只记录。规则写在场景和角色上，三种用法的主要差别都在这里。

主动行为分三档：

- `auto`：照常执行。
- `observe`：照常判断，但对外开口的那一步只记录"本来会做什么、为什么"。草稿不写进会话历史，否则 agent 会以为自己说过。
- `off`：不做。

默认保持当前行为。场景里的主动插话按发言规则对应：点名是 `off`，自由是 `auto`，自由加上 `observe` 开关是 `observe`（见 13.2）。

现状：**部分**。已有管理员/访客、权限模式、执行隔离、群聊积极度、内部群模式与预算、自主活动的次数与预算、Hook 的冻结权限，但分散在各处；场景级规则和 `observe` 档已有（2b），按场景取规则；轮流与导演、私下频道、旁白、回合时钟和轮数结束条件已有（2c）。

### 3.6 记录（Journal）

所有事件、决定、发言、内心活动和花费可靠落盘，按时间排成可回放的时间线。陪伴里它是经历和记忆的来源；团队里用于审计；剧场里用于回放、剪辑和从任意一点分出平行世界。

现状：**部分**。会话历史只追加；经历是有界的派生索引；可靠事件日志和自主活动账本各自记录；分支有不可变快照。缺跨角色的统一时间线（内心活动和发言排在一起）和导出。

### 3.7 两个接口

**执行器（Executor）**：推进承诺的一方。

- 现有实现：内核的一轮 run、后台 Job、本机/SSH/其他节点的代执行、MCP。现状：**已有**。
- 外部 agent（Claude Code、Codex 等）也是一种实现：作为 Job 在工作目录里运行，结果由 nano-agent 自己验收（跑测试、看改动），不采信它们的自述。现状：**未做**。

**出口（Outbox）**：发往渠道和场景的消息。

- 每条消息有稳定 ID 和回执：待发、已发，或已丢弃并附原因。
- 同一目标严格有序；临时失败退避重试；目标永久不可达才丢弃。
- 保证"至少一次"，不承诺恰好一次。

现状：**已有**（第 1 步，2026-10-31）。外部平台渠道的消息经 `internal/outbox` 先落盘再发送，细节见 [运行时](RUNTIME.md#可靠出站与健康状态)。命令行、网页、Job 卡片、审批卡片、Hook 通知和流式回复不经过它，仍走内存协程。

## 4 工作契约

交出去的每件事写清五项。缺哪一项，就会出现对应的问题：

| 要素 | 内容 | 缺了会怎样 |
| --- | --- | --- |
| 目标 | 要做成什么 | 答非所问 |
| 授权 | 谁让做的、在哪个场景、能动到哪里 | 越权，或畏手畏脚 |
| 完成标准 | 用什么证据算做完 | 永远不结束，或假完成 |
| 汇报去处 | 确认、问题、结果发到哪里 | 刷屏，或失联 |
| 停止条件 | 预算、时限、什么时候必须停下来问 | 烧钱、死循环、乱猜 |

**任务分类**看三个问题：一轮能不能做完？有没有交付物？要不要等外部的事？

- 一轮能做完的小事当场做，不建承诺。
- 要多轮、有交付物的事建承诺，交给执行器。
- 要等时间或事件的事，交给来源（定时任务、Hook）。
- 方向还没定的，先问一个具体问题。

**会话**：一件事配一个干活的会话。原对话里只出现三样东西：一次确认、要人回答的问题、最终结果。

**汇报**的状态：进展、等待、就绪、受阻、失败、无需处理；可以附一个要人回答的具体问题。

**结束**只有四种：完成（有证据）、无需处理（有理由）、失败、被人叫停。"在等"不是结束。

分类由接到消息的角色在同一轮里用工具完成，不另设一个先过一遍所有消息的路由会话。

## 5 三种用法的配置

| | 陪伴 | 团队 | 剧场 |
| --- | --- | --- | --- |
| 场景 | 私聊、熟人群 | 团队群 + 代码仓库 | 内部群，可含多个私下频道 |
| 来源 | 主人的消息、作息、定时 | 群消息、Issue/PR/CI | 其他角色的发言、导演插入的事件、场景时钟 |
| 准入 | 主人说的都算 | 名单里的人点名才算，其余只记录 | 发言规则和预算 |
| 承诺 | 约定、回访、定时任务 | 工单 | 角色目标，可以对其他角色保密 |
| 执行器 | 自己的 run、分支 | 分支、外部 agent | 自己的 run，只用场内工具 |
| 出口 | 原对话 | 原消息下的回复、PR | 只在场内 |
| 记录用于 | 经历与记忆 | 审计与面板 | 回放、剪辑、平行世界 |
| 主要指标 | 陪伴感、打扰度 | 注意力、真完成率 | 戏剧性、可复现、单场成本 |

剧场的额外约束：

- 场内角色只能在场内说话、只用场内工具，不接触真实渠道、真实工作目录和主人的会话。
- 每场记录模型、参数和全部输入，能够重放；平行世界从分支快照分出。
- 防刷屏这类阈值是场景规则，不写死在代码里。

团队的额外约束：

- 只在名单里的人点名后开工；没点名的主动工作先用 `observe` 记录。
- 一件事只确认一次，过程不刷屏，结果和问题回到原对话。
- 代码改动在承诺自己的工作区里完成，经验收后交付。

## 6 理论对照

| 层 | 理论 | 用它检查什么 |
| --- | --- | --- |
| 运行时 | Actor 模型 | 角色之间只靠消息交流；消息不丢、不重复，同一目标有序 |
| 单个角色的心智 | BDI（信念—愿望—意图） | 信念、想法、意图分开，意图有进度和证据；对应 `autonomy.State` 的 Beliefs、Ideas、Intentions |
| 多角色场景 | 多智能体系统的角色与规范 | 谁能做什么、谁对谁负责写在规则里，不写在提示词里 |
| 社会模拟 | Generative Agents（记忆流、反思、计划） | 经历、记忆整理、日程是否撑得起角色的连续性 |
| 交办工作 | 委托—代理 | 每件事是否有完整的工作契约 |

## 7 检验标准

1. **架构试金石**：新增一种场景，只写配置、规则和来源/执行器的实现，不在 `App` 的消息入口和 run 启动路径里加特殊分支。如果必须加，说明概念划错了。
2. **场景集**：每种用法维护一组真实输入（每组约 30 条）。每条标明期望的分类、执行器、完成证据和最多打扰人的次数，端到端运行并打分。
3. **指标**：
   - 注意力：每件事打扰人几次，人需要补充说明几次；
   - 真完成率：有证据的完成占多少；
   - 假完成率：声称完成但验收不过；
   - 越权次数；
   - 成本：token 和时长。
   剧场另看可复现性和单场成本。
4. **先观察**：新的判断逻辑先用 `observe` 档在真实流量上只记录，人工对照后再开启。
5. **不变量测试**：
   - 承诺没有证据或理由不能结束；
   - 每个进行中的承诺恰好处在一个阶段；
   - 每条出站消息都有回执；
   - 执行器不能扩大授权；
   - 每个角色模型能看到的内容（系统提示、工具定义）有字节快照和体积上限。

## 8 不做的事

- 不照搬 dsh-superagent 的多人授权机制（准入表、策略版本与授权重校验、后续消息归属、交还）。团队用法需要时只引入准入表和授权记录，并按本文的概念命名。
- 不设每条消息都先经过的路由会话（见第 4 节）。
- 不把 Schedule、Agenda、FollowUp、Hook、分支合并成一个任务对象（见 3.4）。
- 不为新能力引入数据库或常驻服务；持久化沿用可靠事件日志的提交、重放和快照写法。新的记录用单独的文件，不和 Job/Hook 共用容量上限。
- 不放宽现有审批和沙箱。外部 agent 执行器、剧场的场内工具都是显式开启的新模式。

## 9 演进路线

每一步在 `dev/<版本>` 分支上完成（见 [发布流程](RELEASE.md)），默认不改变现有行为。

| 步骤 | 内容 | 服务于 | 前置收敛项 |
| --- | --- | --- | --- |
| 1 事实层（已完成） | 可靠出站（作为从 App 拆出的投递服务）；健康状态（每个部件认领一个条目，只由它写）；模型面快照测试 | 全部 | R1、R12、R3 的投递部分 |
| 2 场景 | 内部群升级为场景：角色提示词、可见性、发言规则、时钟、预算池、结束条件、场内工具；外部群可绑定场景规则，群聊规则以场景为准（agent 上的群聊设置作为没单独设置时的默认值）；主动插话的 `observe` 档。分 2a、2b、2c 三段，见第 13 节 | 全部 | R6 |
| 3 剧场 | 导演台（插入事件、暂停、禁言、分出平行世界、倒带）；统一时间线；导出时间轴字幕；可重放记录 | 剧场 | — |
| 4 承诺 | 共用契约和阶段函数；Report 工具；"等我处理"汇总；分支新增 attention 投递档（只发就绪、问题和受阻，现有 silent 不变） | 陪伴、团队 | R2、R7 |
| 5 团队 | 仓库与团队群来源；准入表与授权记录；工单；外部 agent 执行器；工作目录内的 git worktree 隔离；说话纪律 | 团队 | — |

按表中顺序推进，先做剧场、后做团队（2026-10-31 确定）。剧场没有外部副作用，能用模型替身做端到端验收，直接检验"场景"这个核心抽象，又能最早产出内容；团队要动真实仓库和真实的人，需要实机联调，等承诺层稳定后再做。剧场完成时检查场景的实现里没有为内部群写特殊分支，避免抽象被剧场带偏。

每一步的做法：

1. 开始前，先把这一步的数据结构、接口和存储位置写进本文对应小节，经主人确认后再写代码。
2. 一次只做一步，不跨步顺带实现后面的内容。
3. 完成时按第 7 节验收，并按 [开发说明](HANDOFF.md) 运行相关测试；然后更新本文的现状标记，把实现细节写进对应的现状文档。

### 13.1 2a：工具登记和本轮工具

现状问题（2026-11-01 核实）：

- 网关工具的名字、定义和处理入口散在 `exec.go`（两份名单和一串 if）、`context.go`、`nodes.go` 的 `toolsFor`、`group.go` 的 `groupTools` 默认表和 `agents.go` 的 `toolNames` 里。`toolNames`（网页上填工具白名单用）已经漏了 Session、Job、Hook 和 Diary。
- 网关不检查模型提出的调用是不是这一轮提供过的工具。内核对 Message、Session、Knowledge、FollowUp、SendFile 等“由网关判断”的工具不拦，只要处理器自己的检查放行就会执行。实测：外部群里管理员点名，群聊只提供了 SendFile，模型提出的 Message 调用照样进了处理器。群里其他人的话会进历史，这是提示词注入能利用的口子，场内工具表也因此守不住。

**登记表**：`internal/app/tooldefs.go` 里一张表，每个网关工具一行。

| 字段 | 含义 |
| --- | --- |
| name | 工具名 |
| spec | 生成给模型的定义；返回“现在不提供”时（没配搜索、没有技能）不出现 |
| call | 网关执行入口 |
| state | 是否走 `gateway:tools` 状态租约（现在 `exec.go` 的第一份名单） |
| started | 受理后直接报“开始”；否则先报“排队”（现在的第二份名单：有外部 I/O 的工具） |
| admin | 处理器只给管理员 |
| scene | 能不能出现在群聊和场景的工具表里（现在是 WebSearch、WebFetch、Skill、Knowledge、FollowUp、SendFile） |

从表推出：exec 分发（替掉两份名单和 if 链）、`toolNames`、场景工具的可选范围、网页的工具列表。哪类会话提供哪些工具（`contextParts`、`toolsFor`）仍然写在代码里，但只通过表取定义，不再自己拼。内核工具（Read、Shell 等）和 MCP 工具不进这张表；C 侧的执行策略不变。

**本轮工具**：模型回复里的每个调用，名字必须在这次请求的工具表（`req.Tools`）里。有一个不在，整批不接受、不执行，按现有的未接受提案（`unaccepted_tool_proposal`）记录，原因写“这一轮没有提供工具 X”。处理器里原有的权限检查保留。

**第 1 步的遗留**：

1. 渠道停用（`stopChannel`）时把它从渠道表和快照里去掉。出站里它的待发消息按“渠道暂时不在”等待，重新启用后接着发；删除机器人仍然丢弃（`DropChannel`）。
2. Job 卡片走内存协程、文字走出站，同一个窗口里两者不共用先后顺序：接受这个边界，写进 [运行时](RUNTIME.md) 的已知边界，并删掉第 12 节里的这句。

**验收**：

- 11 份模型面快照不变，`prefixVer` 不变。
- 每个快照角色提供的工具，要么在登记表里，要么是内核工具或 MCP 工具；`toolNames` 包含表里的全部工具。
- 回归：外部群（管理员点名）、内部群成员、访客和整理记忆会话，各提出一个没提供的工具，整批不接受，处理器没有执行。
- 渠道停用再启用，待发消息不丢、按顺序发出。

### 13.2 2b：场景规则

**哪些会话属于哪个场景**：

- 内部群：记录会话 `room:<id>` 和成员会话 `@<agent>/room:<id>`；规则存在群里。
- 外部群：设置里 `Group` 为真、又不属于内部群的会话；规则存在这个会话的设置里。
- 私聊：其余会话。这一步私聊没有规则，行为不变。

新增 `a.sceneOf(sid)`，返回会话所在的场景：种类、键（`room:<id>` 或外部群的会话 ID）、内部群和规则。群聊规则、工具、系统提示里的场景内容、主动插话和预算都从它取。新代码不在 `OnMessage`、`startRun` 和一轮结束的路径里加“是不是群、是不是房间”的判断；改到的旧判断顺手换成场景。

**数据结构**：新建叶子包 `internal/scene`，只放类型、默认值和校验，不依赖其他包。

~~~go
type Rules struct {
	Mode        string          `json:"mode,omitempty"`         // mention | free；2c 再加 turns | director
	Observe     bool            `json:"observe,omitempty"`      // 主动插话只记录，不发出
	Brief       string          `json:"brief,omitempty"`        // 场景说明，每个成员都看得到
	Roles       map[string]Role `json:"roles,omitempty"`        // agent ID → 它在这里的角色
	Tools       []string        `json:"tools"`                  // null 或缺省：沿用默认；[]：不给工具
	Style       Style           `json:"style,omitempty"`
	Guard       Guard           `json:"guard,omitempty"`
	Budget      int             `json:"budget,omitempty"`       // 每天最多多少 token，0 不限
	BudgetTotal int             `json:"budget_total,omitempty"` // 这一场最多多少 token，0 不限
}

type Role struct {
	Prompt    string `json:"prompt,omitempty"`    // 角色提示词
	Eagerness string `json:"eagerness,omitempty"` // off | low | normal | high；空表示沿用 agent 的
}

type Style struct { // 空或 0 表示沿用 agent 的群聊设置
	Quiet  string `json:"quiet,omitempty"`   // 安静多久以后才可能插话
	MinGap string `json:"min_gap,omitempty"` // 两次发言至少隔多久
	MaxLen int    `json:"max_len,omitempty"` // 一条最多多少字（外部群）
	Parts  int    `json:"parts,omitempty"`   // 最多拆成几条（外部群）
}

type Guard struct { // 只用于内部群的点名和自由模式；0 表示默认
	Run      int `json:"run,omitempty"`       // 连续几条 agent 发言就暂停：默认 8，范围 2–50
	PingPong int `json:"ping_pong,omitempty"` // 两个 agent 来回几轮就暂停：默认 6，范围 2–50
}
~~~

- `rooms.Room` 嵌入 `scene.Rules`，去掉自己的 `Mode` 和 `Budget`。JSON 键名不变，旧的 `rooms.json` 原样能读，不迁移。
- 外部群：`session.Settings` 加 `Scene *scene.Rules`（`json:"scene,omitempty"`）。
- `Mode` 为空时：内部群是 mention（和现在建群的默认一样）；外部群是 free，按积极度决定插不插话（现在的行为）。外部群设成 mention 就只在被点名时说话。
- 校验 `scene.Validate(种类)`：外部群只接受 mode（mention、free）、observe、brief、roles、tools、style 和 budget；两个 agent 的私聊 mode 固定为 mention；brief 和每条角色提示词最多 2000 字；tools 只能是登记表里 `scene` 为真的工具；数值不能为负，Guard 在范围内。

**生效顺序**：每一项单独取，前面的有值就用前面的。

| 项 | 顺序 |
| --- | --- |
| 积极度 | 场景角色 → agent 的群聊积极度 → low。工具型 agent 只有在场景角色里明确设了才会主动插话 |
| 说话样式 | 场景 Style → agent 的群聊设置 → 内置默认 |
| 工具 | 场景 Tools → agent 的群聊工具 → 默认表。场景 Tools 有值、agent 也设了群聊工具时取交集。最后去掉这一轮拿不到的（没配搜索、没有技能、不是拟人型就没有 FollowUp 等） |
| 防刷屏 | 场景 Guard → 8 条 / 6 轮 |

agent 上的群聊设置（`group_eagerness`、`group_quiet`、`group_min_gap`、`group_max_len`、`group_parts`、`group_tools`）保留，含义改为“没单独设置的群里用的默认值”，网页上的说明同步改。

**场景说明和角色提示词**：放在成员会话的系统前缀里，紧跟群聊守则，依次是 `[场景] <说明>` 和 `[你的角色] <提示词>`，没有就不加。同一个场景里保持不变；改动只让这个场景成员的前缀缓存失效一次，和改人格一样。工具定义不变，`prefixVer` 不升。

**预算池**：一个场景所有成员会话的用量（输入加输出 token）记在一起，包括 `observe` 的那几轮。

- 状态存在 `data/runtime/scenes.json`：键是场景的键，值是当天日期、当天用量、这一场的累计和开始计数的时间。每轮结束、有变化时，整份写临时文件再替换；重启后接着算。崩溃时可能丢掉最后一轮的累加，可以接受。删群时删掉它的条目。
- 内部群超过任一预算：和现在一样暂停，群记录里写明原因。这一场的累计可以在网页上清零（`PATCH` 带 `reset: true`），重新开始。
- 外部群超过预算：当天不再调用模型，主动插话停止；被点名时每天最多回一次固定说明（“今天的额度用完了”），不调用模型。会话面板显示这个状态。
- 用量在一轮结束时才累加，一轮可能略微超出。

**`observe` 档**：

- 只作用于主动插话：内部群的自由模式，以及外部群按积极度插话的那一轮。被点名的回复、两个 agent 的私聊、Message 工具和 FollowUp 不受影响。
- 那一轮照常请求模型，请求和平时一样，前缀缓存照常命中。回复不写进任何会话历史和群记录，也不发出；模型提出的工具调用不执行。记下本来会说的话（或者本来会调用的工具名和参数摘要）、触发原因（安静了多久、有几条新消息、门槛概率）和用量，然后结束这一轮。宿主为这一轮放进历史的记忆说明可以留着，那不是它说的话。
- 每小时额度和“不想说就越等越久”按判断了一次计，不按说了一次计。
- 记录写进 `data/runtime/observe.jsonl`，用 `internal/journal`；最多保留 2000 条，超了重写，只留最新的一半。写入失败时这一轮的结果丢掉（反正不发），健康状态记为 degraded。
- 网页上，场景的面板列出最近的记录，默认不显示“[不回复]”的判断。

**网页和接口**：

- 内部群面板：场景说明和每个成员的角色提示词放在显眼处；工具、预算、`observe`、说话样式和防刷屏阈值收在“更多规则”里，默认收起。
- 外部群的会话面板加“群规则”，内容同上，没有防刷屏。
- `PATCH /api/rooms/{id}` 接受规则字段；`PATCH /api/sessions/{sid}` 接受 `scene` 整块；`GET /api/observe?scene=<键>&n=50`。

**验收**：

- 没设规则时 11 份快照不变。新增两个快照角色：带说明、角色和工具表的内部群成员；带规则的外部群。
- 旧格式的 `rooms.json` 读入后，生效规则等于现在的行为（夹具测试）。
- 生效顺序表的每一行都有测试；场景工具表里没有的工具，模型提出也不执行（用 2a 的检查）。
- 预算：重启前后累计一致；超了按上面的规则处理，外部群一天只回一次说明。
- `observe`：内部群自由模式和外部群各一组。没有发出，成员历史和群记录里没有，`observe.jsonl` 里有记录；被点名照常回复。
- 试金石：`OnMessage`、`startRun` 和一轮结束的路径里，没有新增内部群或外部群的判断。

### 13.3 2c：场内编排

**一句话的分发**：内部群里的每一句话都走同一个函数 `roomPost(room, line)`，替掉现在 `roomHumanSay`、`roomAgentSay` 和 Message 工具里三段相同的分发循环。

~~~go
type roomLine struct {
	From    string // agent ID；人和旁白为空
	Name    string // 显示名；旁白为“旁白”
	Kind    string // say 说话 | narrate 旁白 | cue 导演只对一个成员说
	Channel string // 私下频道 ID；空表示公开
	To      string // cue 的对象
	Text    string
}
~~~

- 群记录收下每一句，带上标记：`[名字] …`、`[#频道][名字] …`、`[旁白] …`、`[导演→名字] …`。
- 成员会话只收它听得到的：公开的话全体都收；频道里的话只有频道成员收；cue 只有对象收，写作 `[导演] …`。说话的 agent 自己不再收一遍。
- 收完再按发言规则决定叫谁说话。

**规则新增字段**（`scene.Rules`，只用于内部群）：

~~~go
Order    []string  `json:"order,omitempty"`    // 轮流的发言顺序；空表示按成员顺序
Rounds   int       `json:"rounds,omitempty"`   // 轮流时这一场最多几轮
Channels []Channel `json:"channels,omitempty"` // 私下频道，最多 8 个

type Channel struct {
	ID      string   `json:"id"`
	Name    string   `json:"name"`
	Members []string `json:"members"` // 必须是群成员；成员退群时一并去掉
}
~~~

**四种发言规则**：

| 规则 | 谁会说话 | 时钟 |
| --- | --- | --- |
| mention 点名 | 被 @ 或叫到名字的成员；两个 agent 的私聊里对方一定回 | 真实时间 |
| free 自由 | 点名，加上按积极度主动插话 | 真实时间 |
| turns 轮流 | 人或旁白在公开频道说一句之后，按顺序每人说一句为一轮，一轮接一轮 | 回合 |
| director 导演 | 只有导演点到的那一个；@ 和叫名字都不触发 | 回合 |

时钟不单独设置：点名和自由按真实时间，轮流和导演按回合。

轮流：

- 轮到的成员，请求末尾多一句只放在这次请求里的提示（“第 3 轮，轮到你。不想说就只回 [不回复]。”），不写进历史。不等 2 秒，上一位说完立刻叫下一位；被禁言的跳过。
- 轮流时 @ 或叫名字不插队；人中途说话照常进历史，不打乱顺序。
- 一整轮所有人都回 [不回复]：停下来，等下一句人话或旁白，不算暂停。
- 某位成员这一次出错算跳过；连续两次出错（跨轮也算）就暂停，并写明原因。
- 轮数和这一轮下一个轮到谁存在 `data/runtime/scenes.json`。到了 `Rounds` 就暂停，写明“这一场到了 N 轮”；清零后重新计数。轮流模式必须设 `Rounds` 或 `BudgetTotal`，保证有界。
- 不用随机数，也不按真实时间等待：同样的输入加上同样的模型替身，两次跑出的群记录逐字相同。
- 重启或取消暂停后不自动接着跑，等下一句人话或旁白。
- 防刷屏阈值不用于轮流和导演模式，它们由轮数、预算和导演控制。

导演：

- `POST /api/rooms/{id}/cue`，参数 `{agent, note, channel}`。有 note 时先作为 cue 发给这个成员，再叫它在指定频道（空表示公开）说一句。它正在说话时拒绝。
- 第 3 步的导演台在这个接口上做界面。

私下频道：

- 频道里的话只有频道成员听得到；被叫到的成员的回复回到那个频道。
- 频道里只按点名触发（频道里有人点名，或导演 cue 时指定了频道）；轮流和主动插话只在公开频道。
- 成员被叫到频道里说话时，请求末尾提示这一句在哪个频道、谁听得到。

旁白和人的话：`POST /api/rooms/{id}/say`，参数 `{text, as, channel}`。`as` 是“旁白”时记作旁白，否则用这个名字（默认是管理员的显示名）。在网页的群聊记录里直接打字，仍然是公开的人话。

**网页**（只做最小可用，导演台在第 3 步）：发言规则加上轮流和导演；轮流时可以编辑顺序和轮数；导演模式下每个成员旁边一个“让 TA 说”；频道的增删和成员选择；群面板里一个旁白输入框。

**验收**：

- 分发矩阵：公开、频道、cue、旁白四种情况下，每个成员会话收到什么、格式是什么，都有测试。
- 轮流：顺序、跳过禁言、计轮、到轮数暂停、全员不说话就停下、出错跳过和暂停、重启后不续跑；同一个脚本跑两次，群记录逐字相同。
- 导演：@、叫名字和主动插话都不触发；一次 cue 只叫一个；它正在说话时拒绝。
- 频道：不在频道里的成员，会话里没有频道里的话；回复回到频道。
- Message 工具发进群、两个 agent 的私聊、`wait` 等回复的现有测试照常通过。
- 用模型替身做一次端到端：建群、设角色、轮流跑三轮、导演 cue 一次，核对群记录。
