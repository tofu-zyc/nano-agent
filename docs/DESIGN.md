# 设计原则与目标架构

本文是 nano-agent 的目标设计，也是评审新功能的依据：它定义概念、原则和检验标准，并标出每个概念的现状。已实现的行为以 [架构](ARCHITECTURE.md)、[运行时](RUNTIME.md) 和各专题文档为准；本文的现状标记与代码不符时，以代码为准并修正本文。

现状标记：**已有**，代码已实现；**部分**，有零件但缺关键规则；**未做**，只存在于本文。

## 1 定位

一个运行时，三种用法：

- **陪伴**：工具型或拟人型 agent 和主人长期相处，聊天、记事、按约定行动。
- **团队**：agent 进入团队群和代码仓库，接收问题反馈，建立工单，交给执行者修改项目，再把结果送回原来的对话。
- **剧场**：给多个 agent 设定角色，放进同一个场景，观察并记录它们的行为，用于实验和内容创作。

三种用法共用同一套概念和执行底座。差别写在配置和规则里，不各自另起一套系统。

## 2 原则

1. **用最少的人的注意力，换最多做完的事。** 每条消息、每个提问、每个设置和每个面板元素都要说明它换来了什么。agent 只在有人必须行动、或有结果可用时开口：确认一次，问一个具体问题，做完报一次。
2. **模型判断，代码记事实。** 任务分类、做法和结论由模型给出；阶段、预算、权限、证据和谁能做什么由代码从记录推出，不采信模型的自称。完成必须引用真实证据。
3. **先记录，再动作。** 改变状态的决定先可靠落盘，外部动作在提交之后执行。结果不明时先核实，不自动重放。
4. **安全只加不减。** 现有审批、沙箱和权限规则不放宽；新需求用显式开启的新模式满足。剧场的戏剧性来自规则起作用，不来自放宽规则。
5. **前缀缓存优先。** 系统提示和工具定义保持稳定，动态内容追加进消息。改变既有前缀字节就是缓存回归，必须同步更新 `prefixVer`。
6. **概念少，设置少。** 新需求优先成为已有概念的属性或一段提示词，不新增概念；一个默认值适合几乎所有人时，不做成设置。
7. **一切有界。** 队列、记录、缓存、并发和预算都有上限和保留策略；满了明确拒绝或暂停，不静默丢弃。
8. **进程少。** 模型循环由 C 内核控制，业务状态在 Go 网关，执行在节点；不为新能力增加常驻服务。

## 3 核心概念

六个概念和两个接口。新代码、文档和界面使用这些术语；发给人的消息用平常的说法。

### 3.1 角色（Actor）

一个 agent 在某个场景里的一个位置：agent 的人格、模型、工具与权限上限和预算，加上这个位置自己的会话和收件方式。陪主人聊天的人格、派活的前台、写代码的执行者、剧里的人物都是角色，区别只在提示词、工具和消息从哪里来。

- 每个角色有自己视角的会话。普通会话可以换执行 agent；内部会话（life、整理记忆、定时任务、内部群成员）和分支的执行身份固定。
- 可用的工具和权限取 agent 上限、场景允许范围和会话设置的交集。
- 场景可以给角色叠加角色提示词，不修改 agent 自己的人格。角色提示词在一个场景内保持不变，放在成员会话的系统前缀里，不破坏缓存。

现状：**部分**。agent 配置在 `data/agents.json`；各视角已有独立会话（`main`、`tg:<id>`、`@<agent>/room:<id>`、`@<agent>/life`、`cron:<id>`、`hook:<delivery_id>`、分支）。场景级角色提示词已有（2b：`[场景]`、`[你的角色]` 放在成员会话的系统前缀里）。

### 3.2 场景（Scene）

角色和人共处的空间。它规定：

- 成员和各自的角色；
- 可见性：谁能听到谁（公开、私下、旁白）；
- 发言规则：点名、自由、轮流或导演控制；
- 时钟：真实时间或按回合（由发言规则决定，见 13.3）；加速时钟等有了具体需求再加；
- 预算池和结束条件；
- 场内允许的工具和出口。

外部的私聊和群聊、网关内部的群都是场景。规则属于场景，不属于 agent：同一个 agent 在团队群和闲聊群里可以遵守不同的规则。

现状：**部分**。内部群（`rooms.Room`）已有成员、点名/自由两种模式、暂停、禁言、双人私聊和每日 token 预算。2b 起规则属于场景（`internal/scene`，存在群记录或外部群的会话设置里，`a.sceneOf` 取），agent 上的群聊设置是没单独设置时的默认值；防刷屏阈值、预算池、场内工具表、`observe` 档都在场景规则里。缺可见性（第 3 步的导演台之后再看）。

### 3.3 事件（Event）

一条不可变的事实：来源、发出者、所在场景与线程、时间、内容。消息、定时到点、Job 结束、文件变化、仓库评论、导演插入的剧情都是事件。

- **来源（Source）** 产生事件。它定义什么算事件、事件属于哪条线程、该回复到哪里。
- 同一个事件只受理一次。
- 等待某个条件成立属于来源，不让承诺自己睡着等。

现状：**部分**。可靠事件日志（`internal/eventlog`）已记录 `message.received`、run、工具、审批、Job、`file.changed` 和到期事件，Hook 订阅它们；但聊天消息启动 run 仍直接走 `OnMessage`，事件只是旁路。网页事件总线 `events.Bus` 只用于展示，可以丢失，不是这里说的事件。

### 3.4 承诺（Commitment）

跨轮次的一件事。每个承诺都写清工作契约（第 4 节），它的阶段由事实推出。约定（Agenda）、回访（FollowUp）、定时任务（Schedule）、Hook、分支，以及以后的工单和角色的秘密目标，都是承诺的不同种类。

- 各种承诺共用契约字段和阶段推导，但仍是各自独立的对象，保留自己的到期、补跑、取消和验收规则；不合并成一个大任务对象。
- 阶段由一个纯函数从记录推出，表格从上往下第一行命中，每一行都有测试。
- 没有证据或放弃理由，承诺不能结束。

现状：**部分**。约定、意图、回访、定时任务、Hook、分支共用契约和阶段函数（`internal/commit`），有 Report 汇报和"等我处理"（第 4 步）。缺工单（第 5 步）和角色的秘密目标。

### 3.5 规则（Policy）

规则决定：哪些事件能变成承诺（准入）、谁能对谁说话、能用什么工具、能花多少预算、主动行为是执行还是只记录。规则写在场景和角色上，三种用法的主要差别都在这里。

主动行为分三档：

- `auto`：照常执行。
- `observe`：照常判断，但对外开口的那一步只记录"本来会做什么、为什么"。草稿不写进会话历史，否则 agent 会以为自己说过。
- `off`：不做。

默认保持当前行为。场景里的主动插话按发言规则对应：点名是 `off`，自由是 `auto`，自由加上 `observe` 开关是 `observe`（见 13.2）。

现状：**部分**。已有管理员/访客、权限模式、执行隔离、群聊积极度、内部群模式与预算、自主活动的次数与预算、Hook 的冻结权限，但分散在各处；场景级规则和 `observe` 档已有（2b），按场景取规则；轮流与导演、私下频道、旁白、回合时钟和轮数结束条件已有（2c）。

### 3.6 记录（Journal）

所有事件、决定、发言、内心活动和花费可靠落盘，按时间排成可回放的时间线。陪伴里它是经历和记忆的来源；团队里用于审计；剧场里用于回放、剪辑和从任意一点分出平行世界。

现状：**部分**。会话历史只追加；经历是有界的派生索引；可靠事件日志和自主活动账本各自记录；分支有不可变快照。戏（`stage` 群）有场景记录：发言、心里话、模型调用和导演的操作排成一条时间线，可重放、可导出（第 3 步）；普通会话还缺跨角色的统一时间线。

### 3.7 两个接口

**执行器（Executor）**：推进承诺的一方。

- 现有实现：内核的一轮 run、后台 Job、本机/SSH/其他节点的代执行、MCP。现状：**已有**。
- 外部 agent（Claude Code、Codex 等）也是一种实现：作为 Job 在工作目录里运行，结果由 nano-agent 自己验收（跑测试、看改动），不采信它们的自述。现状：**未做**，见 16.4。

**出口（Outbox）**：发往渠道和场景的消息。

- 每条消息有稳定 ID 和回执：待发、已发，或已丢弃并附原因。
- 同一目标严格有序；临时失败退避重试；目标永久不可达才丢弃。
- 保证"至少一次"，不承诺恰好一次。

现状：**已有**（第 1 步，2026-10-31）。外部平台渠道的消息经 `internal/outbox` 先落盘再发送，细节见 [运行时](RUNTIME.md#可靠出站与健康状态)。命令行、网页、Job 卡片、审批卡片、Hook 通知和流式回复不经过它，仍走内存协程。

## 4 工作契约

交出去的每件事写清五项。缺哪一项，就会出现对应的问题：

| 要素 | 内容 | 缺了会怎样 |
| --- | --- | --- |
| 目标 | 要做成什么 | 答非所问 |
| 授权 | 谁让做的、在哪个场景、能动到哪里 | 越权，或畏手畏脚 |
| 完成标准 | 用什么证据算做完 | 永远不结束，或假完成 |
| 汇报去处 | 确认、问题、结果发到哪里 | 刷屏，或失联 |
| 停止条件 | 预算、时限、什么时候必须停下来问 | 烧钱、死循环、乱猜 |

**任务分类**看三个问题：一轮能不能做完？有没有交付物？要不要等外部的事？

- 一轮能做完的小事当场做，不建承诺。
- 要多轮、有交付物的事建承诺，交给执行器。
- 要等时间或事件的事，交给来源（定时任务、Hook）。
- 方向还没定的，先问一个具体问题。

**会话**：一件事配一个干活的会话。原对话里只出现三样东西：一次确认、要人回答的问题、最终结果。

**汇报**的状态：进展、等待、就绪、受阻、失败、无需处理；可以附一个要人回答的具体问题。

**结束**只有四种：完成（有证据）、无需处理（有理由）、失败、被人叫停。"在等"不是结束。

分类由接到消息的角色在同一轮里用工具完成，不另设一个先过一遍所有消息的路由会话。

## 5 三种用法的配置

| | 陪伴 | 团队 | 剧场 |
| --- | --- | --- | --- |
| 场景 | 私聊、熟人群 | 团队群 + 代码仓库 | 内部群，可含多个私下频道 |
| 来源 | 主人的消息、作息、定时 | 群消息、Issue/PR/CI | 其他角色的发言、导演插入的事件、场景时钟 |
| 准入 | 主人说的都算 | 名单里的人点名才算，其余只记录 | 发言规则和预算 |
| 承诺 | 约定、回访、定时任务 | 工单 | 角色目标，可以对其他角色保密 |
| 执行器 | 自己的 run、分支 | 分支、外部 agent | 自己的 run，只用场内工具 |
| 出口 | 原对话 | 原消息下的回复、PR | 只在场内 |
| 记录用于 | 经历与记忆 | 审计与面板 | 回放、剪辑、平行世界 |
| 主要指标 | 陪伴感、打扰度 | 注意力、真完成率 | 戏剧性、可复现、单场成本 |

剧场的额外约束：

- 场内角色只能在场内说话、只用场内工具，不接触真实渠道、真实工作目录和主人的会话。
- 每场记录模型、参数和全部输入，能够重放；平行世界从分支快照分出。
- 防刷屏这类阈值是场景规则，不写死在代码里。

团队的额外约束：

- 只在名单里的人点名后开工；没点名的主动工作先用 `observe` 记录。
- 一件事只确认一次，过程不刷屏，结果和问题回到原对话。
- 代码改动在承诺自己的工作区里完成，经验收后交付。

## 6 理论对照

| 层 | 理论 | 用它检查什么 |
| --- | --- | --- |
| 运行时 | Actor 模型 | 角色之间只靠消息交流；消息不丢、不重复，同一目标有序 |
| 单个角色的心智 | BDI（信念—愿望—意图） | 信念、想法、意图分开，意图有进度和证据；对应 `autonomy.State` 的 Beliefs、Ideas、Intentions |
| 多角色场景 | 多智能体系统的角色与规范 | 谁能做什么、谁对谁负责写在规则里，不写在提示词里 |
| 社会模拟 | Generative Agents（记忆流、反思、计划） | 经历、记忆整理、日程是否撑得起角色的连续性 |
| 交办工作 | 委托—代理 | 每件事是否有完整的工作契约 |

## 7 检验标准

1. **架构试金石**：新增一种场景，只写配置、规则和来源/执行器的实现，不在 `App` 的消息入口和 run 启动路径里加特殊分支。如果必须加，说明概念划错了。
2. **场景集**：每种用法维护一组真实输入（每组约 30 条）。每条标明期望的分类、执行器、完成证据和最多打扰人的次数，端到端运行并打分。
3. **指标**：
   - 注意力：每件事打扰人几次，人需要补充说明几次；
   - 真完成率：有证据的完成占多少；
   - 假完成率：声称完成但验收不过；
   - 越权次数；
   - 成本：token 和时长。
   剧场另看可复现性和单场成本。
4. **先观察**：新的判断逻辑先用 `observe` 档在真实流量上只记录，人工对照后再开启。
5. **不变量测试**：
   - 承诺没有证据或理由不能结束；
   - 每个进行中的承诺恰好处在一个阶段；
   - 每条出站消息都有回执；
   - 执行器不能扩大授权；
   - 每个角色模型能看到的内容（系统提示、工具定义）有字节快照和体积上限。

## 8 不做的事

- 不照搬 dsh-superagent 的多人授权机制（准入表、策略版本与授权重校验、后续消息归属、交还）。团队用法需要时只引入准入表和授权记录，并按本文的概念命名。
- 不设每条消息都先经过的路由会话（见第 4 节）。
- 不把 Schedule、Agenda、FollowUp、Hook、分支合并成一个任务对象（见 3.4）。
- 不为新能力引入数据库或常驻服务；持久化沿用可靠事件日志的提交、重放和快照写法。新的记录用单独的文件，不和 Job/Hook 共用容量上限。
- 不放宽现有审批和沙箱。外部 agent 执行器、剧场的场内工具都是显式开启的新模式。

## 9 演进路线

每一步在 `dev/<版本>` 分支上完成（见 [发布流程](RELEASE.md)），默认不改变现有行为。

| 步骤 | 内容 | 服务于 | 前置收敛项 |
| --- | --- | --- | --- |
| 1 事实层（已完成） | 可靠出站（作为从 App 拆出的投递服务）；健康状态（每个部件认领一个条目，只由它写）；模型面快照测试 | 全部 | R1、R12、R3 的投递部分 |
| 2 场景（已完成） | 内部群升级为场景：角色提示词、可见性、发言规则、时钟、预算池、结束条件、场内工具；外部群可绑定场景规则，群聊规则以场景为准（agent 上的群聊设置作为没单独设置时的默认值）；主动插话的 `observe` 档。分 2a、2b、2c 三段，见第 13 节 | 全部 | R6 |
| 3 剧场（已完成） | 导演台（插入事件、暂停、禁言、分出平行世界、倒带）；统一时间线；导出时间轴字幕；可重放记录。分 3a、3b、3c 三段，见第 14 节 | 剧场 | — |
| 4 承诺（已完成） | 共用契约和阶段函数；Report 工具；"等我处理"汇总；分支新增 attention 投递档（只发就绪、问题和受阻，现有 silent 不变）。分 4a、4b、4c 三段，见第 15 节 | 陪伴、团队 | R2、R7 |
| 5 团队 | 团队群和 GitHub 来源；准入名单与授权记录；工单；每个工单一个 git worktree；外部 agent（登记成命令）；说话纪律。分 5a、5b、5c、5d 四段，见第 16 节 | 团队 | — |

按表中顺序推进，先做剧场、后做团队（2026-10-31 确定）。剧场没有外部副作用，能用模型替身做端到端验收，直接检验"场景"这个核心抽象，又能最早产出内容；团队要动真实仓库和真实的人，需要实机联调，等承诺层稳定后再做。剧场完成时检查场景的实现里没有为内部群写特殊分支，避免抽象被剧场带偏。

每一步的做法：

1. 开始前，先把这一步的数据结构、接口和存储位置写进本文对应小节，经主人确认后再写代码。
2. 一次只做一步，不跨步顺带实现后面的内容。
3. 完成时按第 7 节验收，并按 [开发说明](HANDOFF.md) 运行相关测试；然后更新本文的现状标记，把实现细节写进对应的现状文档。

### 13.1 2a：工具登记和本轮工具

现状问题（2026-11-01 核实）：

- 网关工具的名字、定义和处理入口散在 `exec.go`（两份名单和一串 if）、`context.go`、`nodes.go` 的 `toolsFor`、`group.go` 的 `groupTools` 默认表和 `agents.go` 的 `toolNames` 里。`toolNames`（网页上填工具白名单用）已经漏了 Session、Job、Hook 和 Diary。
- 网关不检查模型提出的调用是不是这一轮提供过的工具。内核对 Message、Session、Knowledge、FollowUp、SendFile 等“由网关判断”的工具不拦，只要处理器自己的检查放行就会执行。实测：外部群里管理员点名，群聊只提供了 SendFile，模型提出的 Message 调用照样进了处理器。群里其他人的话会进历史，这是提示词注入能利用的口子，场内工具表也因此守不住。

**登记表**：`internal/app/tooldefs.go` 里一张表，每个网关工具一行。

| 字段 | 含义 |
| --- | --- |
| name | 工具名 |
| spec | 生成给模型的定义；返回“现在不提供”时（没配搜索、没有技能）不出现 |
| call | 网关执行入口 |
| state | 是否走 `gateway:tools` 状态租约（现在 `exec.go` 的第一份名单） |
| started | 受理后直接报“开始”；否则先报“排队”（现在的第二份名单：有外部 I/O 的工具） |
| admin | 处理器只给管理员 |
| scene | 能不能出现在群聊和场景的工具表里（现在是 WebSearch、WebFetch、Skill、Knowledge、FollowUp、SendFile） |

从表推出：exec 分发（替掉两份名单和 if 链）、`toolNames`、场景工具的可选范围、网页的工具列表。哪类会话提供哪些工具（`contextParts`、`toolsFor`）仍然写在代码里，但只通过表取定义，不再自己拼。内核工具（Read、Shell 等）和 MCP 工具不进这张表；C 侧的执行策略不变。

**本轮工具**：模型回复里的每个调用，名字必须在这次请求的工具表（`req.Tools`）里。有一个不在，整批不接受、不执行，按现有的未接受提案（`unaccepted_tool_proposal`）记录，原因写“这一轮没有提供工具 X”。处理器里原有的权限检查保留。

**第 1 步的遗留**：

1. 渠道停用（`stopChannel`）时把它从渠道表和快照里去掉。出站里它的待发消息按“渠道暂时不在”等待，重新启用后接着发；删除机器人仍然丢弃（`DropChannel`）。
2. Job 卡片走内存协程、文字走出站，同一个窗口里两者不共用先后顺序：接受这个边界，写进 [运行时](RUNTIME.md) 的已知边界，并删掉第 12 节里的这句。

**验收**：

- 11 份模型面快照不变，`prefixVer` 不变。
- 每个快照角色提供的工具，要么在登记表里，要么是内核工具或 MCP 工具；`toolNames` 包含表里的全部工具。
- 回归：外部群（管理员点名）、内部群成员、访客和整理记忆会话，各提出一个没提供的工具，整批不接受，处理器没有执行。
- 渠道停用再启用，待发消息不丢、按顺序发出。

### 13.2 2b：场景规则

**哪些会话属于哪个场景**：

- 内部群：记录会话 `room:<id>` 和成员会话 `@<agent>/room:<id>`；规则存在群里。
- 外部群：设置里 `Group` 为真、又不属于内部群的会话；规则存在这个会话的设置里。
- 私聊：其余会话。这一步私聊没有规则，行为不变。

新增 `a.sceneOf(sid)`，返回会话所在的场景：种类、键（`room:<id>` 或外部群的会话 ID）、内部群和规则。群聊规则、工具、系统提示里的场景内容、主动插话和预算都从它取。新代码不在 `OnMessage`、`startRun` 和一轮结束的路径里加“是不是群、是不是房间”的判断；改到的旧判断顺手换成场景。

**数据结构**：新建叶子包 `internal/scene`，只放类型、默认值和校验，不依赖其他包。

```go
type Rules struct {
	Mode        string          `json:"mode,omitempty"`         // mention | free；2c 再加 turns | director
	Observe     bool            `json:"observe,omitempty"`      // 主动插话只记录，不发出
	Brief       string          `json:"brief,omitempty"`        // 场景说明，每个成员都看得到
	Roles       map[string]Role `json:"roles,omitempty"`        // agent ID → 它在这里的角色
	Tools       []string        `json:"tools"`                  // null 或缺省：沿用默认；[]：不给工具
	Style       Style           `json:"style,omitempty"`
	Guard       Guard           `json:"guard,omitempty"`
	Budget      int             `json:"budget,omitempty"`       // 每天最多多少 token，0 不限
	BudgetTotal int             `json:"budget_total,omitempty"` // 这一场最多多少 token，0 不限
}

type Role struct {
	Prompt    string `json:"prompt,omitempty"`    // 角色提示词
	Eagerness string `json:"eagerness,omitempty"` // off | low | normal | high；空表示沿用 agent 的
}

type Style struct { // 空或 0 表示沿用 agent 的群聊设置
	Quiet  string `json:"quiet,omitempty"`   // 安静多久以后才可能插话
	MinGap string `json:"min_gap,omitempty"` // 两次发言至少隔多久
	MaxLen int    `json:"max_len,omitempty"` // 一条最多多少字（外部群）
	Parts  int    `json:"parts,omitempty"`   // 最多拆成几条（外部群）
}

type Guard struct { // 只用于内部群的点名和自由模式；0 表示默认
	Run      int `json:"run,omitempty"`       // 连续几条 agent 发言就暂停：默认 8，范围 2–50
	PingPong int `json:"ping_pong,omitempty"` // 两个 agent 来回几轮就暂停：默认 6，范围 2–50
}
```

- `rooms.Room` 嵌入 `scene.Rules`，去掉自己的 `Mode` 和 `Budget`。JSON 键名不变，旧的 `rooms.json` 原样能读，不迁移。
- 外部群：`session.Settings` 加 `Scene *scene.Rules`（`json:"scene,omitempty"`）。
- `Mode` 为空时：内部群是 mention（和现在建群的默认一样）；外部群是 free，按积极度决定插不插话（现在的行为）。外部群设成 mention 就只在被点名时说话。
- 校验 `scene.Validate(种类)`：外部群只接受 mode（mention、free）、observe、brief、roles、tools、style 和 budget；两个 agent 的私聊 mode 固定为 mention；brief 和每条角色提示词最多 2000 字；tools 只能是登记表里 `scene` 为真的工具；数值不能为负，Guard 在范围内。

**生效顺序**：每一项单独取，前面的有值就用前面的。

| 项 | 顺序 |
| --- | --- |
| 积极度 | 场景角色 → agent 的群聊积极度 → low。工具型 agent 只有在场景角色里明确设了才会主动插话 |
| 说话样式 | 场景 Style → agent 的群聊设置 → 内置默认 |
| 工具 | 场景 Tools → agent 的群聊工具 → 默认表。场景 Tools 有值、agent 也设了群聊工具时取交集。最后去掉这一轮拿不到的（没配搜索、没有技能、不是拟人型就没有 FollowUp 等） |
| 防刷屏 | 场景 Guard → 8 条 / 6 轮 |

agent 上的群聊设置（`group_eagerness`、`group_quiet`、`group_min_gap`、`group_max_len`、`group_parts`、`group_tools`）保留，含义改为“没单独设置的群里用的默认值”，网页上的说明同步改。

**场景说明和角色提示词**：放在成员会话的系统前缀里，紧跟群聊守则，依次是 `[场景] <说明>` 和 `[你的角色] <提示词>`，没有就不加。同一个场景里保持不变；改动只让这个场景成员的前缀缓存失效一次，和改人格一样。工具定义不变，`prefixVer` 不升。

**预算池**：一个场景所有成员会话的用量（输入加输出 token）记在一起，包括 `observe` 的那几轮。

- 状态存在 `data/runtime/scenes.json`：键是场景的键，值是当天日期、当天用量、这一场的累计和开始计数的时间。每轮结束、有变化时，整份写临时文件再替换；重启后接着算。崩溃时可能丢掉最后一轮的累加，可以接受。删群时删掉它的条目。
- 内部群超过任一预算：和现在一样暂停，群记录里写明原因。这一场的累计可以在网页上清零（`PATCH` 带 `reset: true`），重新开始。
- 外部群超过预算：当天不再调用模型，主动插话停止；被点名时每天最多回一次固定说明（“今天的额度用完了”），不调用模型。会话面板显示这个状态。
- 用量在一轮结束时才累加，一轮可能略微超出。

**`observe` 档**：

- 只作用于主动插话：内部群的自由模式，以及外部群按积极度插话的那一轮。被点名的回复、两个 agent 的私聊、Message 工具和 FollowUp 不受影响。
- 那一轮照常请求模型，请求和平时一样，前缀缓存照常命中。回复不写进任何会话历史和群记录，也不发出；模型提出的工具调用不执行。记下本来会说的话（或者本来会调用的工具名和参数摘要）、触发原因（安静了多久、有几条新消息、门槛概率）和用量，然后结束这一轮。宿主为这一轮放进历史的记忆说明可以留着，那不是它说的话。
- 每小时额度和“不想说就越等越久”按判断了一次计，不按说了一次计。
- 记录写进 `data/runtime/observe.jsonl`，用 `internal/journal`；最多保留 2000 条，超了重写，只留最新的一半。写入失败时这一轮的结果丢掉（反正不发），健康状态记为 degraded。
- 网页上，场景的面板列出最近的记录，默认不显示“[不回复]”的判断。

**网页和接口**：

- 内部群面板：场景说明和每个成员的角色提示词放在显眼处；工具、预算、`observe`、说话样式和防刷屏阈值收在“更多规则”里，默认收起。
- 外部群的会话面板加“群规则”，内容同上，没有防刷屏。
- `PATCH /api/rooms/{id}` 接受规则字段；`PATCH /api/sessions/{sid}` 接受 `scene` 整块；`GET /api/observe?scene=<键>&n=50`。

**验收**：

- 没设规则时 11 份快照不变。新增两个快照角色：带说明、角色和工具表的内部群成员；带规则的外部群。
- 旧格式的 `rooms.json` 读入后，生效规则等于现在的行为（夹具测试）。
- 生效顺序表的每一行都有测试；场景工具表里没有的工具，模型提出也不执行（用 2a 的检查）。
- 预算：重启前后累计一致；超了按上面的规则处理，外部群一天只回一次说明。
- `observe`：内部群自由模式和外部群各一组。没有发出，成员历史和群记录里没有，`observe.jsonl` 里有记录；被点名照常回复。
- 试金石：`OnMessage`、`startRun` 和一轮结束的路径里，没有新增内部群或外部群的判断。

### 13.3 2c：场内编排

**一句话的分发**：内部群里的每一句话都走同一个函数 `roomPost(room, line)`，替掉现在 `roomHumanSay`、`roomAgentSay` 和 Message 工具里三段相同的分发循环。

```go
type roomLine struct {
	From    string // agent ID；人和旁白为空
	Name    string // 显示名；旁白为“旁白”
	Kind    string // say 说话 | narrate 旁白 | cue 导演只对一个成员说
	Channel string // 私下频道 ID；空表示公开
	To      string // cue 的对象
	Text    string
}
```

- 群记录收下每一句，带上标记：`[名字] …`、`[#频道][名字] …`、`[旁白] …`、`[导演→名字] …`。
- 成员会话只收它听得到的：公开的话全体都收；频道里的话只有频道成员收；cue 只有对象收，写作 `[导演] …`。说话的 agent 自己不再收一遍。
- 收完再按发言规则决定叫谁说话。

**规则新增字段**（`scene.Rules`，只用于内部群）：

```go
Order    []string  `json:"order,omitempty"`    // 轮流的发言顺序；空表示按成员顺序
Rounds   int       `json:"rounds,omitempty"`   // 轮流时这一场最多几轮
Channels []Channel `json:"channels,omitempty"` // 私下频道，最多 8 个

type Channel struct {
	ID      string   `json:"id"`
	Name    string   `json:"name"`
	Members []string `json:"members"` // 必须是群成员；成员退群时一并去掉
}
```

**四种发言规则**：

| 规则 | 谁会说话 | 时钟 |
| --- | --- | --- |
| mention 点名 | 被 @ 或叫到名字的成员；两个 agent 的私聊里对方一定回 | 真实时间 |
| free 自由 | 点名，加上按积极度主动插话 | 真实时间 |
| turns 轮流 | 人或旁白在公开频道说一句之后，按顺序每人说一句为一轮，一轮接一轮 | 回合 |
| director 导演 | 只有导演点到的那一个；@ 和叫名字都不触发 | 回合 |

时钟不单独设置：点名和自由按真实时间，轮流和导演按回合。

轮流：

- 轮到的成员，请求末尾多一句只放在这次请求里的提示（“第 3 轮，轮到你。不想说就只回 [不回复]。”），不写进历史。不等 2 秒，上一位说完立刻叫下一位；被禁言的跳过。
- 轮流时 @ 或叫名字不插队；人中途说话照常进历史，不打乱顺序。
- 一整轮所有人都回 [不回复]：停下来，等下一句人话或旁白，不算暂停。
- 某位成员这一次出错算跳过；连续两次出错（跨轮也算）就暂停，并写明原因。
- 轮数和这一轮下一个轮到谁存在 `data/runtime/scenes.json`。到了 `Rounds` 就暂停，写明“这一场到了 N 轮”；清零后重新计数。轮流模式必须设 `Rounds` 或 `BudgetTotal`，保证有界。
- 不用随机数，也不按真实时间等待：同样的输入加上同样的模型替身，两次跑出的群记录逐字相同。
- 重启或取消暂停后不自动接着跑，等下一句人话或旁白。
- 防刷屏阈值不用于轮流和导演模式，它们由轮数、预算和导演控制。

导演：

- `POST /api/rooms/{id}/cue`，参数 `{agent, note, channel}`。有 note 时先作为 cue 发给这个成员，再叫它在指定频道（空表示公开）说一句。它正在说话时拒绝。
- 第 3 步的导演台在这个接口上做界面。

私下频道：

- 频道里的话只有频道成员听得到；被叫到的成员的回复回到那个频道。
- 频道里只按点名触发（频道里有人点名，或导演 cue 时指定了频道）；轮流和主动插话只在公开频道。
- 成员被叫到频道里说话时，请求末尾提示这一句在哪个频道、谁听得到。

旁白和人的话：`POST /api/rooms/{id}/say`，参数 `{text, as, channel}`。`as` 是“旁白”时记作旁白，否则用这个名字（默认是管理员的显示名）。在网页的群聊记录里直接打字，仍然是公开的人话。

**网页**（只做最小可用，导演台在第 3 步）：发言规则加上轮流和导演；轮流时可以编辑顺序和轮数；导演模式下每个成员旁边一个“让 TA 说”；频道的增删和成员选择；群面板里一个旁白输入框。

**验收**：

- 分发矩阵：公开、频道、cue、旁白四种情况下，每个成员会话收到什么、格式是什么，都有测试。
- 轮流：顺序、跳过禁言、计轮、到轮数暂停、全员不说话就停下、出错跳过和暂停、重启后不续跑；同一个脚本跑两次，群记录逐字相同。
- 导演：@、叫名字和主动插话都不触发；一次 cue 只叫一个；它正在说话时拒绝。
- 频道：不在频道里的成员，会话里没有频道里的话；回复回到频道。
- Message 工具发进群、两个 agent 的私聊、`wait` 等回复的现有测试照常通过。
- 用模型替身做一次端到端：建群、设角色、轮流跑三轮、导演 cue 一次，核对群记录。

## 14 第 3 步：剧场

目标：内部群可以当一场戏来演。场内的事不进 agent 的记忆，场外的事也进不来；每一句话、每一次模型调用、成员的心里话和导演的操作排成一条时间线，记录足以重放；可以从任意一句分出平行世界；能导出字幕和剧本；导演在一个页面上完成全部操作。分三段做，每段单独验收：

| 3c | 导演台、导出和放映 |

### 14.1 3a：戏的隔离和记录

现状：**已有**（3a，2026-11-01）。实现细节见 [运行时](RUNTIME.md#剧场)。

**规则新增字段**（`scene.Rules`，只用于内部群，不用于两个 agent 的私聊）：

```go
Stage bool `json:"stage,omitempty"` // 这是一场戏：场内的事不进成员的记忆，场外进不来，全程记录
Inner bool `json:"inner,omitempty"` // 心里话：成员每次先写一句心里想的，别人听不到，记进时间线；只用于 stage
```

- `stage` 只能在建群时设，之后不能改：关掉以后，下一次整理记忆会把整场戏当成日记读进去。分出的平行世界照抄。
- `inner` 可以随时开关，改的是系统前缀，下一轮生效。

**隔离**（`stage` 的群；都按 `sceneOf(sid)` 取到的规则判断，不判断"是不是房间"）：

场内的事不出去：

- 成员会话不记经历（`recordRunExperience`），整理记忆不读它（`diarySources`）。
- 成员会话的请求不附记忆说明、经历和"想起来的记忆"（`memoryNotes` 返回空）。戏里只有人格、场景说明、角色和场内的话。
- 工具只能从 WebSearch、WebFetch 里选，`tools` 不设时不给工具。Knowledge 会写进 agent 的真实记忆，FollowUp、SendFile、Skill 在戏里没有用处，都不提供。登记表加一个 `stage` 属性标出可选的两个，网页和校验都从登记表取。

场外的事不进来：

- Message 工具不能发进 `stage` 的群，谁发都拒绝（"这是一场戏，只能在导演台说话"）；内心活动的聊天对象里不列它。
- 人的话、旁白和 cue 只从网页进来（群聊记录里打字、`/say`、`/cue`）。

**场景记录**：每个 `stage` 群一份 `data/runtime/stage/<群 ID>.jsonl`，用 `internal/journal` 写，单条最大 64KB，整份最大 64MB。不开 `stage` 的群没有这份记录。删群时一并关闭并删除它的场景记录，分出的平行世界有自己的一份。

```go
type StageRec struct {
	Kind string `json:"kind"` // line | cursors | run | model | prefix | op | fork
	TS   int64  `json:"ts"`   // 毫秒
	// line：群记录里的一句
	Line    int            `json:"line,omitempty"`    // 群记录里的第几句（从 1 起，取群记录会话当前的长度加一；场景记录里允许有空位）
	From    string         `json:"from,omitempty"`    // agent ID；人、旁白、系统为空
	Name    string         `json:"name,omitempty"`
	Say     string         `json:"say,omitempty"`     // say | narrate | cue | system
	Channel string         `json:"channel,omitempty"`
	To      string         `json:"to,omitempty"`
	Text    string         `json:"text,omitempty"`
	Cursors map[string]int `json:"cursors,omitempty"` // 可以从这句分出时：这句送达后每个成员会话的消息数（见 14.2）
	// run：成员的一轮结束；model：一次模型调用
	Run       string    `json:"run,omitempty"`
	Member    string    `json:"member,omitempty"`
	Status    string    `json:"status,omitempty"`
	Inner     string    `json:"inner,omitempty"`     // 心里话（最多 200 字）
	Reasoning string    `json:"reasoning,omitempty"` // 模型的推理，最多 8000 字
	Usage     *llm.Usage `json:"usage,omitempty"`
	Said      int       `json:"said,omitempty"`      // 这一轮说出口的是第几句；没说为 0
	Model     *ModelRec `json:"model,omitempty"`
	// prefix：某个前缀第一次出现时记一次全文；op：导演的操作；fork：从哪一场的第几句分出（放在 Detail 里）
	Hash   string          `json:"hash,omitempty"`
	Body   string          `json:"body,omitempty"`
	Op     string          `json:"op,omitempty"`     // pause | resume | mute | rules | reset
	Detail json.RawMessage `json:"detail,omitempty"`
}

type ModelRec struct {
	Endpoint string         `json:"endpoint"` // 模型接口的名字
	Model    string         `json:"model"`
	Params   map[string]any `json:"params"`   // 实际发出的参数（现在网关只发 thinking 和 max_tokens）
	Prefix   string         `json:"prefix"`   // 系统提示加工具定义的 SHA-256，全文在 prefix 记录里
	Input    string         `json:"input"`    // 这次请求全部消息的 SHA-256
	Msgs     [2]int         `json:"msgs"`     // 用到的成员会话消息：[Base, 长度)
	Tail     []string       `json:"tail"`     // 只放在这次请求里的内容（轮到你、频道提示等）
	Out      string         `json:"out"`      // 回复正文
	Calls    []llm.ToolCall `json:"calls,omitempty"`
	Reason   string         `json:"reason"`   // 结束原因
}
```

字段名可以按实现调整，但每类记录要能回答这些问题：这一句是谁、在哪、对谁说的；这一轮是谁跑的、想了什么、说没说、花了多少；每次模型调用用的是哪个模型和参数、看到了什么（前缀全文和消息哈希）、回了什么；导演做了什么。

`Cursors` 单独成一条 `cursors` 记录：`line` 要在送达之前写下，`Cursors` 要在送达之后才能取（见 14.2）。

- **先记再做**：群记录的每一句先写进场景记录，再写群记录、送给成员。群记录只有一个写入口（`roomPost` 和 `pauseRoom` 都经过它）。`Line` 取这一句在群记录里的实际位置，不单独计数。写不进去（满了或者磁盘出错）就不发这一句，暂停这一场并写明原因；这条暂停提示只写群记录，场景记录里这个位置空着。健康条目 `stage` 由网关认领一次：任何一场写不进去就是 degraded，并写明是哪几场；那一场再写成功后移出。
- 模型调用和一轮结束的记录走同一个场景钩子：没有场景记录的会话什么都不做。消息入口和 run 的启动、结束路径里不加"是不是剧场"的判断。
- 导演的操作（暂停、恢复、禁言、改规则、清零）记为 `op`。

**心里话**（`inner`）：

- 场景说明后面加一段固定的说明，放进系统前缀，同一场内不变：回复先写 `<心里>一句心里话</心里>`，再写说出口的话；不想说话，就在心里话后面只回 [不回复]。
- 网关把回复拆开：心里话记进时间线，别人只听到说出口的部分；成员自己的会话保留完整回复，它记得自己想过什么。没按格式写的，整段当作说出口的话。
- 心里话最多 200 字，超出截断。

**接口**：`GET /api/rooms/{id}/timeline?after=<序号>&n=200` 按序返回记录；`prefix` 记录在这里只给哈希和长度，全文用 `GET /api/rooms/{id}/timeline/prefix/<hash>` 取。每写一条记录发一个网页事件 `stage`（群 ID 和最新序号），网页按序号增量取。

**重放**：记录要足以重放，验收时用一个只在测试里的重放驱动来证明：按时间线，把人和旁白的话在同样的位置说出，模型调用按记录的输出回答。不做成产品功能，网页上的"重来"是 14.2 的分出。

**验收**：

- 隔离：`stage` 群跑过几轮后，成员的经历、整理记忆的输入、Knowledge 里都没有场内的内容；成员的请求里没有记忆说明和经历；Message 发进来被拒；内心活动的聊天对象里没有它；工具只能选 WebSearch 和 WebFetch。对照：同样的群不开 `stage`，行为和现在一样。
- 记录：轮流脚本跑三轮，每一句、每一轮、每次模型调用都有记录，`Line` 就是这句在群记录里的位置；写入失败时这一句不发、群暂停、健康状态变化。
- 重放：重放驱动跑出的群记录逐字相同，每次调用的 `Input` 哈希相同。
- 心里话：能拆开；回 [不回复] 时也记心里话；没按格式时整段算说出口；别的成员的会话里没有心里话。
- 快照：新增 `room-member-stage` 快照（开 `stage` 和 `inner`）。原有快照不变，`prefixVer` 不变。

### 14.2 3b：平行世界和倒带

现状：**已有**（3b，2026-11-01）。实现细节见 [运行时](RUNTIME.md#平行世界和倒带)。

`POST /api/rooms/{id}/fork`，参数 `{at, name, rewind}`：从第 `at` 句分出新的一场。

- **新群**：成员、禁言、规则照抄原群现在的（含 `stage`）；名字默认"<原名> · 平行 N"。不暂停：轮流和导演模式照常等下一句人话、旁白或 cue。第 `at` 句之后才进群的成员（`Cursors` 里没有）从空白开始；之后退群的不带过去。
- **群记录**：原群记录的前 `at` 句。
- **成员会话**：每个成员取原会话的前 `Cursors[成员]` 条消息，从头开始，不带原会话的压缩摘要；太长时照常压缩。
- **场景记录**：原记录里到第 `at` 句为止的部分（包括用到的 `prefix` 记录）用 `Rewrite` 整份写进新文件，再追加一条 `fork {from, at}`。"到第 `at` 句为止"截到第 `at` 句的 `cursors` 记录；说出这一句的那一轮的 `run` 记录（`Said` 等于 `at`）写在 `cursors` 后面，也要带上，不然这一句的心里话和用量就丢了。
- **用量**：从零开始（`total`、`round`、`next` 都清零）。轮流从顺序的第一位开始。
- **原来那场**：不受影响。记录只追加，不删、不截。
- **倒带**：`rewind: true` 时，分出后再暂停原来那场。网页上叫"从这句重来"。

**能分出的句子**：只有"场上没人在说话"的时刻能分出，也就是这一句送达时，除了说出这一句的成员，没有成员在跑或排队。只在这样的句子上记 `Cursors`。在别的句子上分出会被拒绝，同时告诉用户最近一个可以分出的句子。轮流和导演模式下几乎每一句都满足。

**写入顺序**：新群最后才出现在群列表里；中途失败，就把已经写的删掉。会话存储加一个 `Seed(sid, msgs)`：只用于新会话，整份写临时文件再替换；会话已存在就拒绝。

**一场戏的记录只追加**：`Line` 是群记录里的位置，`Cursors` 是成员会话里的位置，都假定这些会话只追加。所以一场戏的群记录和成员会话不能清空、撤回、删历史（全部或轮次范围）、删会话，网页的这四个入口都拒绝，错误写明"这是一场戏的记录，只能追加：要重来就从某一句分出平行世界，不要了就删群"。按 `sceneOf(sid)` 的规则判断，在任何副作用之前（清空上下文遇到正在跑的会话会先停掉它，判断要在这之前）。压缩照常，它只挪 `Base`，不动文件。不拦的话，群记录清空后 `Line` 会从 1 重新数，成员会话清空后再长回来，`Cursors` 指到的就是清空之后的内容，分出的平行世界拿到的是错的。

**验收**：

- 轮流脚本跑三轮，从第一轮结束的那一句分出：新群的群记录等于原群记录的前 N 句；每个成员会话等于原会话的前缀；场景记录到第 N 句为止相同（包括这一句那一轮的 `run`，心里话还在），最后一条是 `fork`。
- 一场戏的群记录和成员会话：清空上下文、撤回、删历史、删会话都被拒绝，会话没变；不是戏的群照旧能删。
- 在新群里说一句不同的旁白，接着跑：原群的群记录、成员会话、场景记录都没变。
- 在不能分出的句子上分出被拒绝，并给出最近一个可以分出的句子。
- 倒带：原群被暂停，新群可以接着跑。
- 新群里 `stage` 的隔离照样生效。

### 14.3 3c：导演台、导出和放映

现状：**已有**（3c，2026-11-01）。实现细节见 [运行时](RUNTIME.md#导演台导出和放映)。

**导出**：`GET /api/rooms/{id}/export?format=srt|md|json&inner=1&channels=1&from=&to=`。`from`、`to` 是句子序号，默认导出整场。

- **字幕（SRT）**：
  - 人和 agent 的公开发言、旁白各占一条，前面写名字（"小鲍：…"），旁白不写名字。
  - `channels=1` 时，频道里的话写成"小鲍（私下）：…"；`inner=1` 时，心里话放在那句话前面，写成"（小鲍心里）…"。cue 和系统提示不进字幕。
  - 时间不用真实时间（里面含有等模型的时间），按阅读速度排：每条时长为字数（整条字幕，含名字）÷ 5 秒，最短 1.5 秒、最长 8 秒，条与条之间留 0.3 秒。超过 40 字的句子按句号、问号、感叹号拆成几条。
- **剧本（Markdown）**：标题、场景说明、角色表、正文。正文里心里话用斜体，暂停写成一行说明。频道里的话和 cue 都算私下的内容，和字幕用同一个开关：`channels=1` 时才出现，并标出来。末尾附这一场的轮数和 token 用量。
- **JSON**：范围内的时间线记录，加上成员、规则和用量合计。

**导演台**：每个 `stage` 群有一个整页的导演台，从群面板的"打开导演台"进去。

- **时间线**（左边）：
  - 每句话一行。心里话、频道里的话、cue、系统提示可以分别显示或隐藏。
  - 能分出的句子旁边有"从这里分出"和"从这句重来"。
  - 点开一轮，可以看推理和用量。
- **控制**（右边）：旁白（公开或某个频道）、人的话；每个成员的"让 TA 说"和禁言；暂停和恢复；轮数和预算的用量；导出。
- **实时更新**：收到 `stage` 事件后增量取时间线。

**放映**：导演台上点"放映"，按时间线一句一句放出来，时间和字幕相同，可以选 1× 或 2×。默认只显示发言和旁白，心里话和频道按开关显示：两个开关在放映前和放映中都能切换，放映中切换就从当前这一句按新的开关接着放。放映开始后新来的句子不插进这一遍。画面适合直接录屏。

**验收**：

- 导出：同一个脚本场导出的 SRT 和 Markdown 有逐字节的快照测试；长句拆分、时长上下限、开关的组合都有测试。
- 网页检查脚本覆盖：打开导演台，显示和隐藏心里话，以旁白身份说一句，从某一句分出后跳到新群，三种格式都能导出，放映能开始和停止。
- 第 3 步收尾：按第 9 节检查场景的实现里没有为内部群写特殊分支，消息入口和 run 的启动、结束路径只按场景规则走。

## 15 第 4 步：承诺

已完成（2026-11-03，最后一个提交 `04369d9`），已实现的行为见 [运行时](RUNTIME.md#承诺阶段和-report)。下面保留各段的设计，供第 5 步引用。

目标：约定、回访、定时任务、Hook、分支这几种承诺共用一份工作契约和一套阶段推导；主人在一个地方看到"等我处理"的事；干活的会话用 Report 汇报，原对话里只出现确认、要人回答的问题和结果。各种承诺仍是各自的对象，保留自己的到期、补跑、取消和验收规则（见 3.4）。分三段做，每段单独验收；后一段等前一段审过再开始：

| 段 | 内容 |
| --- | --- |
| 4a | 前置收敛：自主活动只留一份状态（R2）；启动一轮之前的准入检查只写一份（R7）。不改变行为 |

默认不改变现有行为：没用 Report、没开 attention 时，消息、投递和存储都和现在一样。只有多了 Report 工具的几类会话（life、分支、定时任务、Hook）快照会变。消息入口和 run 的启动路径不加分支，准入统一走 `admitRun`。

第 11 节的前两项在这一步定下来：

2. 工单作为承诺的新种类单独建对象（第 5 步做），共用这里的契约和阶段函数，不从 Agenda 扩展。Agenda 是一个拟人 agent 自己的日程，存在它的心智状态里；工单属于团队场景，有外部来源（Issue、PR）、执行器、工作区和授权记录，放进 Agenda 会把团队的东西带进陪伴的心智状态。

### 15.2 4b：契约、阶段和 Report

现状：**已有**（4b，2026-11-02）。实现细节见 [运行时](RUNTIME.md#承诺阶段和-report)。

**种类**：

| 种类 | 是什么 |
| --- | --- |
| `agenda` | 议程项 |
| `intention` | 意图；只列没有未完成议程项的，有的话只列议程项 |
| `followup` | 约好过会儿再看 |
| `schedule` | 定时任务 |
| `hook` | Hook 规则，不是单次投递 |
| `branch` | 分支 |

只列还存在的：删掉的、已经结束超过 30 天的都不列。

**契约**：第 4 节的五项，从各自的字段推出来，不另存一份。

```go
package commit

type Contract struct {
	Goal     string   // 目标
	By       string   // 授权：谁让做的
	Scene    string   // 授权：在哪个会话或场景
	Scope    string   // 授权：能动到哪里（权限模式、工作目录、工具），一句话
	Done     string   // 完成标准；没写就是空
	ReportTo []string // 汇报去处；空表示只留在自己的记录里
	Stop     string   // 停止条件：预算、时限、次数，一句话
}
```

| 种类 | 目标 | 授权 | 完成标准 | 汇报去处 | 停止条件 |
| --- | --- | --- | --- | --- | --- |
| agenda | `Title`，有意图时加上意图的 `Why` | agent；`Source`；`Workspaces`、`Mode` | `Criteria` | life 会话 | 每日自主预算、作息；`Minutes` |
| intention | `Title`、`Why` | agent；`SourceEvent` | 有证据的执行结果 | life 会话 | `BudgetTokens`、每日自主预算 |
| followup | `Note` | 那个聊天 | 到点说一句或不说 | 那个聊天 | 一次 |
| schedule | `Name` | `CreatedBy`、`CreatorMode`、`Mode`、`Workspaces` | 每次跑完的结果 | `Deliver`；`Silent` 时为空 | `Timeout`；一次性的跑一次 |
| hook | `Name` | `Creator`、冻结的 `Scope` | 每次投递成功 | `Deliver` | `TokenBudget`、`Retries`、`DeadlineAt`、`Once` |
| branch | `Intent`，没有就用 `Title` | `CreatedBy`、`OwnerAgent`、快照里的设置 | 主人引入结论或归档 | 投递档；silent 为空 | 自动分支的层数、当日自主预算 |

**阶段**：一共九个。前五个是进行中，后四个是结束，对应第 4 节的四种结束。

| 阶段 | 含义 |
| --- | --- |
| `waiting` 等待 | 没到时间、在等事件，或到期了但还不能开始 |
| `running` 进行中 | 有一轮正在跑 |
| `blocked` 受阻 | 要人处理：有没回答的问题、汇报受阻或失败、上一次失败、结果不明，或者说结束了却没有证据或理由 |
| `ready` 就绪 | 有结果等人看，还没看过 |
| `paused` 暂停 | 人停下的，可以恢复 |
| `done` 完成 | 有证据 |
| `dropped` 无需处理 | 有理由 |
| `failed` 失败 | 不再重试 |
| `stopped` 叫停 | 人取消或归档的 |

阶段由一个纯函数从事实推出：

```go
type Facts struct {
	Now      int64
	Ended    string // 自己的记录里已经结束：done | dropped | failed | stopped
	Evidence string // done 的证据
	Reason   string // dropped、failed、stopped 的理由
	Paused   bool
	Running  bool
	Question string // 还没回答的问题
	Blocked  string // 受阻的原因
	Ready    string // 等人看的结果
	Mark     string // Blocked、Ready、Question 来自哪一条事实；"知道了"和回答都靠它
	Due      int64  // 下一次到期；0 表示在等事件
	Wait     string // 到期了还不能开始的原因
}

func Phase(f Facts) (phase, why string)
```

从上往下，第一行命中就是结果，每一行一个测试：

| # | 条件 | 阶段 | why |
| --- | --- | --- | --- |
| 1 | `Ended` 是 done，`Evidence` 空 | blocked | 说做完了，但没有证据 |
| 2 | `Ended` 是 dropped、failed 或 stopped，`Reason` 空；或者 `Ended` 不是这四种 | blocked | 说结束了，但没写理由（不认识的就写出这个值） |
| 3 | `Ended` 不空 | 同 `Ended` | `Evidence` 或 `Reason` |
| 4 | `Paused` | paused | |
| 5 | `Running` | running | |
| 6 | `Question` 不空 | blocked | 等你回答：`Question` |
| 7 | `Blocked` 不空 | blocked | `Blocked` |
| 8 | `Ready` 不空 | ready | `Ready` |
| 9 | `Due > Now` | waiting | 等到某个时间 |
| 10 | `Due > 0`，`Wait` 不空 | waiting | `Wait` |
| 11 | `Due > 0` | waiting | 到期了，马上开始 |
| 12 | 其余 | waiting | 等事件 |

另有两个不变量测试：任意一组事实都恰好得到九个阶段中的一个；得到结束阶段时，一定带着证据或理由。

第 2 行会把没有理由的结束当成要人处理，所以主人自己做的结束，适配函数一定给出理由：网页上取消日程没写理由，记成"主人取消了"；归档、取消分支没有备注，记成"主人归档了""取消了"。

**事实**：从各自的记录推出。适配函数写在 app 里，一种一个，各有测试。

| 事实 | agenda | intention | followup | schedule | hook | branch |
| --- | --- | --- | --- | --- | --- | --- |
| Ended | done → done（`Result`）；cancelled → 主人取消的是 stopped（没有 `Result` 就写"主人取消了"），agent 取消的和升级前没记谁取消的是 dropped（没有 `Result` 就写"取消了"）；skipped → dropped | done → done（`Evidence`）；failed → failed；cancelled 同 agenda | — | 一次性任务跑过、已停用：`Last.OK` 为真是 done（`Last.Summary`），否则 failed | `Once` 且成功后停用：done（最后一次投递的 `Result`）；`Once` 已被事件占用、那次投递最终失败或取消：failed（投递的 `Error`） | archived、cancelled → stopped |
| Paused | 自主活动暂停 | 同左，或 paused | —（暂停时回访照常发） | 停用，且不是已结束的一次性任务 | 停用（`Once` 规则被事件占用后自己停用的不算） | paused |
| Running | in_progress | running | — | `Running` | 有投递在跑 | running、queued |
| Blocked | 汇报 | 汇报 | — | 上一次失败（`Last.OK` 为假）；汇报 | 最近一次投递 failed 或 uncertain（结果不明）；汇报 | needs_attention（`Note`）；汇报 |
| Ready | 汇报 | 汇报 | — | 汇报 | 汇报 | 主人建的分支做完一轮（completed），之后没引入过结论（`ReportedAt`）；汇报 |
| Due | `At` | `NextAt` | `At` | `Next` | `DeadlineAt`（毫秒，换成秒），只在这个时间的事件还没触发时 | preparing、pending_boundary、ready：`CreatedAt` |
| Wait | 意图的 `Blocked` | `Blocked` | — | — | — | preparing、pending_boundary：等源会话的安全边界；ready：等开始 |

- 表里的"汇报"，指这件事最近一条要主人知道的 Report（ready、blocked、failed、not_needed），而且还没看过也没回答过：
  - blocked、failed 进 `Blocked`，带着问题的进 `Question`；
  - ready、not_needed 进 `Ready`。
  - progress、waiting 只记一笔，不顶掉前面那条还没处理的汇报。
- 汇报和宿主自己的事实同时有时，按阶段表的先后取一个：问题先于受阻，受阻先于就绪。汇报的受阻、问题压过宿主的就绪；宿主的受阻压过汇报的就绪；两边都是受阻时取汇报的（它更具体）。`Mark` 跟着决定阶段的那条事实；主人点过"知道了"，下一条才显出来。
- 升级前已经引入过结论的分支没有 `ReportedAt`：`Progress` 是引入结论时写的那句（"已把结论带回来源会话：……"），就算已经引入过。
- 宿主自己记下的 `Blocked`、`Ready` 也带 `Mark`：
  - 汇报：`r:<序号>`；
  - 上一次失败：`last:<时间>`；
  - 投递：`d:<投递 ID>`；
  - 分支做完一轮：`p:<ProgressAt>`。

  主人点过"知道了"的 `Mark` 不再算。
- 自主活动分出的分支（`autonomousForker`）做完一轮不算 Ready，只看它的汇报。不然 agent 自己探索的每一轮都会进"等我处理"。
- 为了分清 agenda 是谁取消的，`AgendaItem` 加一个 `EndedBy` 字段（`owner` 或 `agent`）。模型调用 `Agenda cancel` 时 `note` 必填，写不做的理由；网页上的取消记 `owner`。

**Report 工具**：干活的会话用它向主人汇报。

```json
{"status": "progress | waiting | ready | blocked | failed | not_needed",
 "text": "说明（最多 500 字）",
 "question": "要主人回答的一个具体问题（最多 200 字，只用于 blocked）",
 "evidence": ["本轮验收凭据的 id"]}
```

- 哪些会话有：life 会话、分支、定时任务、Hook 的 agent 处理器。
  - 普通聊天和群聊没有：在原对话里直接回复就是汇报。戏里也没有。
  - 这几类会话的工具表因此变化：`prefixVer` 加一，快照更新；其他会话的快照内容不变，只有金样第一行的 `prefixVer` 跟着改。
  - 工具结果开头的"[本轮验收凭据]"现在只在有 Agenda 的会话里给模型看；有 Report 的会话也要给，不然分支、定时任务、Hook 里的 ready 拿不到凭据。
- 汇报的是哪件事，由宿主从这一轮推出，不由模型填：
  - life 的这一轮看 `mindRun.Trigger`：议程项优先，其次意图。自己安排的检查不对应任何承诺，Report 拒绝。
  - 分支汇报的是分支自己。
  - 定时任务汇报的是这个任务。
  - Hook 汇报的是这条规则；这一轮跑在分支里也算 Hook。
- 代码检查：
  - `ready` 至少要有一个 `evidence`，按 Agenda done 的规则核验，必须是本轮真实成功的工具结果。
  - `blocked`、`failed`、`not_needed` 要有 `text`。
  - `question` 只能和 `blocked` 一起用。
  - Hook 和定时任务的这一轮结束后，没有会话接着问，所以带 `question` 的拒绝，它们只汇报状态。
  - 一轮最多调用 4 次。
- 汇报只记录"主人需要知道什么"，不改承诺自己的状态：做完、取消日程仍然用 Agenda，分支的生命周期仍由主人决定。阶段从事实推出，所以汇报会通过上面的表影响阶段。
- 工具说明和 life 技能里写清楚什么时候该汇报：
  - 有结果可用（ready）；
  - 卡住了，要人处理（blocked，可以问一个问题）；
  - 做不下去了（failed）；
  - 不用做了（not_needed）。

  progress、waiting 只记一笔，不会发给任何人。

### 15.3 4c：等我处理和 attention

现状：**已有**（4c，2026-11-02）。实现细节见 [运行时](RUNTIME.md#承诺阶段和-report)。

**等我处理**：所有阶段为 blocked 或 ready 的承诺，最新的在前。只给管理员看。

- 还有没回答的问题的，就算这件事正在跑（阶段是 running）也列进来，也能回答：分支汇报了问题之后这一轮往往还没结束，主人收到通知马上回答不能被拒绝。回答排到下一个安全边界。
- 结束了却没写理由或证据的（阶段表第 1、2 行判成 blocked 的）没有 `Mark`，点不了"知道了"，只在"全部承诺"里显示。

- 网页：
  - 拓扑图上有一个"等我处理 N"的标记，N 为 0 时不显示。
  - 点开是一个面板，不新增页面，左边仍然只有拓扑和会话两个页面。
  - 每件事一行：agent、种类和标题、阶段和 why、问题。操作有"回答"（有问题时才有）、"知道了"、"打开"。
  - 面板底部可以展开"全部承诺"，按阶段分组。
- 聊天，只在管理员窗口：
  - `/pending` 列出同样的内容，每件事带一个编号：有汇报的用汇报序号，没有的用 `Mark`。
  - `/answer <编号> <回答>` 回答问题。
  - `/seen <编号>` 等于点"知道了"。
- 接口：
  - `GET /api/pending`
  - `POST /api/pending/seen {kind, id, mark}`
  - `POST /api/pending/answer {kind, id, mark, text}`，回答最多 2000 字。

  "知道了"和回答都先写进承诺记录（`seen`、`answer`）再生效。

  汇报的就绪盖住了宿主自己的就绪时（比如主人建的分支做完一轮，这一轮里也 Report ready 了），两条说的是同一件事：点"知道了"时两个 `Mark` 一起记 `seen`，不要让主人点两次。受阻和就绪互相盖住时不这样，它们是两件不同的事。

**回答送到哪里**：回答写进记录之后，作为"主人的回答"送到这件事干活的地方。

- 分支：放进分支会话的下一个安全边界，像"继续"一样接着跑。分支已归档就拒绝回答。
- 议程项、意图：在 agent 的心智状态里加一个事件，带上议程项或意图的 ID 和回答。议程项还没开始的，时间改成现在，下一次自主活动就处理它，回答出现在"要处理的"里。
- 定时任务、Hook 不接受回答：它们的 Report 不能带问题（见 15.2），没有要回答的东西。
- 回答过的问题不再算 `Question`。
- 主人在这些地方自己动手也算处理过：
  - 分支引入结论、继续或归档后，之前的汇报都算看过。
  - 定时任务下一次成功后，上一次失败不再算。

**attention 投递档**：分支的第三种投递档。`silent` 和 `report` 的行为不变。

- 和 `silent` 一样安静：`branchSilent` 为真，普通回复、工具进度、Message、SendFile 等都不往外发。
- 唯一的例外：这个分支的 Report 是 ready、blocked 或 failed 时，发一条到父会话最近的窗口（原对话）。宿主自己记下的失败（这一轮出错，needs_attention）也当作受阻发一条。
- 发出去的只是通知，不写进父会话的历史，父会话的 agent 不会以为是自己说的。格式：

```text
[分支「<标题>」· 就绪] <text>

[分支「<标题>」· 需要你回答] <text>
问：<question>
回复 /answer <编号> <你的回答>，或在网页的"等我处理"里回答。
```

- 怎么发：
  - 外部渠道经可靠出站发送，网页发一个 `say` 事件。
  - 先写记录，再入队。入队前崩溃的那一条只留在"等我处理"里，不补发。
- 有界：
  - 状态和正文都跟上一条推送一样的，不发。
  - 每个分支每小时最多发 3 条，多出来的只留在"等我处理"里。
  - 父会话本身是安静的（silent 分支、安静来源），不发。
- 谁能设：和 `report` 一样，只有主人明确要求才行，比如 `/session fork` 带参数、主人会话里的 Session 工具（网页现在没有分出分支的入口，以后加的时候也给这个选项）。
  - "主人会话"指主人在里面聊天的普通会话。定时任务、分支、life、Hook、整理记忆这些会话里的 Session 工具只能分出 `silent`：它们没有主人在看的窗口，通知要么发不到人，要么是自主活动替主人开了一个会打扰他的口子。
- 契约的汇报去处（`ReportTo`）是父会话，和 `report` 一样。
- attention 分支的系统提示里多一句：有结果时用 Report ready 汇报，卡住时用 Report blocked 问一个具体问题；其他时候主人看不到你。`branchNote` 从 F1 起没人调用，删掉。

**验收**：

- 等我处理：
  - 受阻、就绪的几种承诺都列出来；点"知道了"之后不再列。
  - 回答之后：分支接着跑；议程项被叫起来，回答出现在"要处理的"里；定时任务下一次的说明里带着回答。
- attention：
  - ready、blocked（带问题）、宿主记下的失败，各发一条到原对话；progress、waiting 和普通回复不发。
  - 同样的汇报不重复发；超过每小时 3 条的不发；父会话安静时不发。
  - 自主活动分出的分支设不成 attention。
  - silent、report 分支的行为和现在一样。
- 网页检查脚本覆盖：标记的数字、打开面板、回答、知道了、"全部承诺"的分组。`/pending`、`/answer`、`/seen` 有端到端测试。
- 第 4 步收尾：按第 7 节检查，承诺的实现没有在消息入口和 run 的启动路径里加分支；"每个进行中的承诺恰好处在一个阶段"和"没有证据或理由不能结束"两条不变量有测试。

## 16 第 5 步：团队

目标：agent 进入团队群和 GitHub 仓库；名单里的人点名后，agent 建一个工单。工单在自己的 git worktree 里由一个分支完成，需要时由分支调用外部 agent 命令。宿主跑验收命令，通过后推分支、开 PR，结果回到原来的对话。原对话里只出现一次确认、要人回答的问题和最终结果（第 4 节）。

分四段做，每段单独验收；后一段等前一段审过再开始：

| 段 | 内容 |
| --- | --- |
| 5a | 团队场景和工单：场景规则里的团队设置（准入名单、仓库工作目录、验收命令）；工单对象和记录；Ticket 工具；授权记录；工单接进承诺列表和等我处理；工单的消息只回原对话。还不动代码 |
| 5b | 工作区、执行和验收：每个工单一个 git worktree；干活的分支；宿主跑验收命令、宿主提交；返工有上限；先交付到本地分支 |
| 5c | GitHub：仓库连接（token，轮询或 webhook，按仓库选）；GitHub 渠道（议题和 PR 是对话）；推分支、开 PR；跟踪 PR 和 CI。网关发起的执行可以带环境变量 |
| 5d | 外部 agent：登记成命令，按工作目录显式开启，只有它自己看得到登录目录 |

默认不改变现有行为：没设团队规则的群、没连接仓库时，一切照旧。Ticket 工具只出现在设了团队规则的会话里，其他会话的快照不变。

消息入口和 run 的启动路径不加分支：

- GitHub 是一个渠道；
- PR 和 CI 的状态是事件来源；
- 工单是承诺的一种，共用第 15 节的契约和阶段函数。

开始前单独提一个只做 gofmt 的提交。hooks_test.go、interject_journal_test.go、life_policy_test.go、proto/proto.go、session/store.go 在 main 上就没格式化。之后每段都检查 `gofmt -l` 为空。

### 16.1 5a：团队场景和工单

**团队规则**：场景规则加一项 `Team`，用于外部群和 5c 的 GitHub 议题。

```go
type Team struct {
	Roster    []string `json:"roster"`           // 准入名单：能派活的人（渠道身份，如 feishu:ou_x、tg:123、gh:alice）；管理员总算在内
	Workspace string   `json:"workspace"`        // 仓库所在的工作目录 ID（data/workspaces.json）
	Check     string   `json:"check,omitempty"`  // 验收命令，在工单的 worktree 里跑，如 make test；空表示只看有没有改动
	Budget    int      `json:"budget,omitempty"` // 每个工单最多多少 token，默认 2000000
}
// scene.Rules 加 Team *Team `json:"team,omitempty"`
```

- 设了团队规则的群：
  - 发言规则固定为点名（`mention`），主动插话固定为 `observe`。
  - 网页上外部群的场景设置里编辑这几项。
- 准入：
  - 名单里的人点名 agent，agent 才能建工单。
  - 不在名单里的人点名，agent 可以回话，但 Ticket create 拒绝，说要名单里的人来派。
  - 谁派的看这一轮的触发消息（`run.from` 和消息 ID），不采信模型填的。
  - 不做 dsh-superagent 的授权重校验、后续消息归属和交还（第 8 节）。

**工单**：承诺的新种类 `ticket`，代码在 `internal/ticket`。

```go
type Ticket struct {
	ID    string `json:"id"` // tk-<序号>
	Agent string `json:"agent"`
	Title string `json:"title"`
	Goal  string `json:"goal"` // 要做成什么，模型写，最多 2000 字
	Auth  Auth   `json:"auth"` // 授权记录，建的时候定下，之后不变
	Check  string `json:"check"`  // 验收命令，建的时候从团队规则取
	Budget int    `json:"budget"`
	Status string `json:"status"` // open | working | checking | ready | done | dropped | failed | stopped | paused
	Reason string `json:"reason,omitempty"`
	// 5b
	Worktree string `json:"worktree,omitempty"`
	Branch   string `json:"branch,omitempty"`    // git 分支 nano/tk-<序号>
	Base     string `json:"base,omitempty"`      // 从哪个提交开始
	RunSID   string `json:"run_sid,omitempty"`   // 干活的分支会话
	Commit   string `json:"commit,omitempty"`    // 验收通过后宿主做的提交
	CheckLog string `json:"check_log,omitempty"` // 最近一次验收：退出码和最后 40 行
	Rework   int    `json:"rework,omitempty"`
	// 5c
	PR string `json:"pr,omitempty"`
	Created, Updated int64
}

type Auth struct {
	By        string   `json:"by"`        // 谁派的（名单里的身份）
	Scene     string   `json:"scene"`     // 在哪个场景（团队群或议题的会话）
	Source    Source   `json:"source"`    // 原消息：渠道、对话、消息 ID、开头 200 字
	Workspace string   `json:"workspace"` // 能动到哪里
	Mode      string   `json:"mode"`      // 权限模式，不超过工作目录和 agent 的上限
	Tools     []string `json:"tools"`     // 场景工具表和 agent 上限的交集
	At        int64    `json:"at"`
}
```

- 存储：`data/runtime/tickets.jsonl`，用 `internal/journal`，单条 16KB，整份 16MB。
  - 每次改动写一条完整的工单，重放时每个 ID 留最后一条。
  - 超过 8MB 时整份重写，结束超过 30 天的丢掉。
  - 先记再说：写不进去就返回错误，健康条目 `tickets` 变 degraded。
- 编号 `tk-<序号>`，序号取记录里的最大值加一。

**Ticket 工具**：只给设了团队规则的会话（团队群、16.3 的议题会话）。

```json
{"action": "create | list | show | note | accept | cancel",
 "title": "…", "goal": "…", "id": "tk-…", "text": "…"}
```

- `create`：建工单，状态 open。
  - 同一条原消息只建一个：按 `Auth.Source` 去重，重试返回同一个工单。
  - 派活的人不在名单里、场景没设团队规则、仓库工作目录不在线：拒绝。
  - 返回里写清：在回复里确认一次；过程不用说，结果和问题会自动发回这里。
- `note`：名单里的人后来补充的话，转进工单。工单在跑时排到分支的下一个安全边界，和回答一样。
- `accept`：名单里的人收下一个就绪的工单（5b 交付到本地分支时用；连了 GitHub 的仓库以 PR 合并为准，没有这一项）。
- `cancel`：名单里的人或管理员叫停，要写理由，结束为 stopped。
- `list`、`show`：只读。

**说话纪律**：

- 原对话里只出现三样：
  - 建工单那一轮 agent 自己的确认；
  - 要人回答的问题；
  - 最终结果。
- 问题和结果由宿主发，作为原消息的回复（`deliver` 带 `replyTo`）。外部渠道走可靠出站。
- 和 attention 一样先在承诺记录里写 `notify` 再入队；同样去重，每个工单每小时最多 3 条。
- 工单的进展、工具输出、分支里的回复都不发到群里。

**契约和事实**（`ticketCommit`，接进 `commitItems`）：

- 契约：
  - 目标：`Goal`。
  - 授权：`Auth`。
  - 完成标准：验收命令通过、开了 PR。5c 之前是验收通过、提交在本地分支。
  - 汇报去处：原消息。
  - 停止条件：预算，返工最多 2 次。
- 事实：

| 事实 | 工单 |
| --- | --- |
| Ended | done：PR 合并了（证据是合并提交），5c 之前是有人 `accept`（证据是提交和验收结果）；dropped：not_needed 汇报（理由）；failed：主人在受阻时放弃（理由）；stopped：叫停（理由）、PR 被关掉没合并 |
| Paused | paused |
| Running | working、checking |
| Blocked | 返工用完验收还没过；预算用完；推送或开 PR 失败；汇报 |
| Ready | PR 开着等人合并（Mark `pr:<号>`）；5c 之前是验收通过、已提交（Mark `c:<提交>`）；汇报 |
| Due | — |
| Wait | open：等开工（5a 里一直是这个） |

- 在工单的分支里调用 Report，汇报的是这个工单，不是分支。
- 回答问题：送进工单的分支，和分支一样排到下一个安全边界。5a 里还没有分支，拒绝回答。
- 网页：工单出现在等我处理和全部承诺里，种类叫"工单"；"打开"打开工单的分支（5a 是来源会话）。主人能在网页上叫停。

**验收**：

- 名单里的人点名后建出工单，授权记录对；不在名单里的人建不了；同一条消息重试只有一个工单。
- 工单进承诺列表，open 是等待；叫停后是 stopped 并有理由；重启后工单还在。
- 群里只有 agent 自己的一次确认，工单不往群里发别的。
- 没设团队规则的群和私聊：快照不变，没有 Ticket 工具。设了团队规则的群新增一份金样。

### 16.2 5b：工作区、执行和验收

**网关发起的执行**：建 worktree、跑验收命令、提交、推送都由宿主做，不经过模型。沿用 Hook 命令处理器的执行方式（`hook_command.go`）：明确的读写范围，结果进事件日志。

**worktree**：每个工单一个，开工时建。

- 位置：`<仓库>/.nano/worktrees/tk-<序号>`，并把 `/.nano/` 写进 `<仓库>/.git/info/exclude`（不提交），主仓库的 `git status` 看不到它。
- 建法：`git -C <仓库> worktree add -b nano/tk-<序号> <位置> <起点>`。
  - 起点是默认分支当前的提交；有远端时先 `fetch`。
  - 起点记进 `Base`。
- 登记成一个派生工作目录（`Workspace.Ticket` 是工单 ID）：
  - 网页上挂在仓库工作目录下；
  - 不能选给别的会话；
  - 权限模式不超过仓库工作目录的。
- 工单结束后删掉 worktree 和这条登记。git 分支留到交付完。

**干活的分支**：从派活的那个会话分出来，带着到派活那条消息为止的上下文。

- 工作目录是工单的 worktree，权限模式是 `Auth.Mode`，工具是 `Auth.Tools`。
- 沙箱：
  - 可写：worktree，和它自己的 git 目录 `<仓库>/.git/worktrees/tk-<序号>`；
  - 只读：`<仓库>/.git` 的其余部分。
  - 所以分支里能改文件、`git status`、`git diff`；`git add`、提交、改 ref、改仓库的 hooks 都做不到。提交由宿主做。
- 投递：和 silent 一样安静。
  - Report ready 触发验收（下面）。
  - blocked、failed 按说话纪律发回原消息。
  - 都不发到父会话。
- 第一条消息是开工说明：目标、验收命令，以及"不要提交或推送；改完用 Report ready，附上你跑过的测试"。

**验收**：分支 Report ready 后，宿主在 worktree 里跑验收命令 `Check`，超时 30 分钟。

- 通过（退出码 0，并且有改动）：
  - 宿主 `git add -A` 并提交：作者用 agent 的名字，提交说明是标题加工单号。
  - 记 `Commit` 和 `CheckLog`，状态 ready。
- 没改动，或退出码不是 0：
  - `Rework` 加一，把验收输出的最后 40 行作为一条消息放进分支的下一个安全边界，接着跑。
  - `Rework` 到 2 还没过：状态 blocked，问派活的人："验收没过……继续改、放弃，还是先收下？"
- 验收结果是证据，不采信分支的自述（第 2 条原则）。

**预算**：工单分支用掉的 token 超过 `Budget` 时，停下这一轮，状态 blocked，理由是预算用完了。回答"继续"再给一份。

**交付（5c 之前）**：本地分支 `nano/tk-<序号>`。

- 结果发回原消息："改好了：<改动摘要>。验收 <命令> 通过，提交 <短号> 在本地分支 nano/tk-<序号>。"
- 名单里的人 `accept` 后，工单 done，删掉 worktree。

**验收**：用临时目录里的真 git 仓库和模型替身。

- 建 worktree；分支只能写 worktree，提交不了。
- 主仓库的工作区、分支和 hooks 不被改动。
- 验收命令过与不过；返工两次后受阻；预算用完受阻。
- 结束后 worktree 清理掉。
- 重启后：
  - 在跑的工单接着跑，或明确受阻；
  - 不重复建 worktree，不重复提交。

### 16.3 5c：GitHub

**仓库连接**：`data/repos.json`，在网页上仓库工作目录的设置里填。

```go
type Repo struct {
	ID        string     `json:"id"`
	Workspace string     `json:"workspace"`          // 本地克隆所在的工作目录
	Owner     string     `json:"owner"`
	Name      string     `json:"name"`
	Base      string     `json:"base"`               // 默认分支
	Token     string     `json:"token"`              // 加密存（internal/secret）
	Bot       string     `json:"bot"`                // token 对应的 GitHub 账号
	Intake    string     `json:"intake"`             // poll（默认）| webhook
	Interval  int        `json:"interval,omitempty"` // 轮询间隔秒，默认 120，最少 60
	Secret    string     `json:"secret,omitempty"`   // webhook 的签名密钥，加密存
	Team      scene.Team `json:"team"`               // 议题对话的团队规则（名单用 gh:<账号>）
}
```

- token：
  - 用细粒度 token：内容、PR、议题读写，检查只读。
  - 只在网关里用：不进模型、不进工具参数、不进命令行参数。
- 要用一个单独的 GitHub 账号。用主人自己的账号时，主人自己的评论会被当成 agent 发的而忽略。网页上写明这一点。

**事件怎么进来**：两种都做，每个仓库选一种。

- 轮询：
  - 每 `Interval` 秒，用 `since` 和 ETag 取新议题、新评论，以及工单相关 PR 的状态和检查结果。
  - 游标存在仓库连接的状态文件里。
- webhook：`POST /api/repos/{id}/webhook`。
  - 不要登录，但必须校验 `X-Hub-Signature-256`。
  - 正文最多 1MB。
  - 只认 issues、issue_comment、pull_request、pull_request_review、pull_request_review_comment、check_suite。
  - 先记，再回 2xx。
  - 网关要能从公网访问，这由主人自己配。网页上显示要填的地址和密钥。
- 两种方式都按 GitHub 的事件或投递 ID 去重，同一件事只受理一次。PR 和检查的状态进事件日志（`repo.*`），由工单读取。

**GitHub 渠道**（`internal/channel/github.go`）：议题和 PR 是对话，正文和评论是消息。

- 对话 ID 是 `owner/name#号`；发消息就是发评论，`replyTo` 忽略；照常走可靠出站。
- 点名：正文里有 `@<Bot>`。
  - 名单里的人点名才算；
  - 其余的只记进事件日志，不进会话。
  - 不在名单里的人写的议题正文和评论，不交给模型。
- 议题会话的场景规则用仓库连接上的 `Team`。
- Ticket 工具在这里同样可用：工单的原消息是这个议题，问题和结果都回到议题里。

**网关发起的执行可以带环境变量**：

- 内核的执行请求加一个 `env`，只有网关发起的执行能带，模型的工具调用不能。
- 推送时凭据走 `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_0`、`GIT_CONFIG_VALUE_0`，传一个 `http.extraheader`，不写文件、不进参数。

**交付**：验收通过、宿主提交之后：

- 推送：网关发起的执行 `git push origin nano/tk-<序号>`。
- 开 PR：网关调 API。
  - 标题是工单标题；正文写目标、谁派的、原消息链接、验收命令和结果。
  - 记 `PR`，状态 ready（Mark `pr:<号>`）。
  - 结果发回原消息：PR 链接和一句摘要。
- 之后：
  - PR 合并了：done，证据是合并提交，不再发消息；删掉 worktree 和本地分支。
  - PR 被关掉、没合并：stopped，理由是 PR 被关了。
  - PR 上的 CI 失败：算一次返工，上限同 5b。
  - 名单里的人在 PR 上提的审阅意见：作为 `note` 送进分支，不算返工次数。
- 推送或开 PR 失败：blocked，带上错误。重试前先查远端分支和 PR 在不在，不重放已经成功的那一步。

**验收**：用本地的假 GitHub（httptest）。

- 轮询和 webhook 各自收到议题、评论、PR 和检查事件，重复的只受理一次。
- 签名不对的 webhook 被拒。
- 名单外的人点名不进会话。
- 推送的命令行参数里没有 token。
- PR 合并、关闭、CI 失败各自推出对的阶段。
- 实机联调由主人在一个测试仓库上做。

### 16.4 5d：外部 agent

Claude Code、Codex 都是命令行程序，不做原生适配，登记成命令就能用。

现在还用不了，差在登录凭据。沙箱本来就允许联网，但执行器把 HOME 换成了沙箱的目录，可读写的也只有工作目录。所以它们找不到也写不了自己的登录目录（`~/.claude`、`~/.codex`）。

```go
type ExternalAgent struct {
	Name string            `json:"name"`          // claude、codex
	Argv []string          `json:"argv"`          // 命令模板，{prompt} 换成这次的要求
	Dirs []string          `json:"dirs"`          // 它自己的配置和登录目录，可读写
	Env  map[string]string `json:"env,omitempty"` // 比如 CLAUDE_CONFIG_DIR、CODEX_HOME
}
```

例如：`{"name": "claude", "argv": ["claude", "-p", "{prompt}"], "dirs": ["~/.claude"], "env": {"CLAUDE_CONFIG_DIR": "~/.claude"}}`。

- 登记和开启：
  - 主人在网页上登记，存在 `data/external-agents.json`。
  - 在工作目录上显式开启哪些能用（`Workspace.External []string`），默认都不开。
  - 工单的 worktree 继承仓库工作目录的开关。
- 工具：新工具 `External`，参数 `name` 和 `prompt`。只出现在开启了外部 agent 的工作目录的会话里。
  - 网关按模板拼出参数，不经 shell。
  - `Dirs` 只加进这一个进程的可读写范围，`Env` 只加进它的环境。
  - 作为后台 Job 在 worktree 里跑，用 Job 工具看输出。
  - 同一会话里的普通 Shell 调用看不到这些目录。
- 这是对沙箱的放宽：开启后，这个外部 agent 能读写自己的登录凭据，也能联网。
  - 网页上开启时写明这一点。
  - 只在名单里的人派的工单里有意义。议题正文是不可信的输入。
- 它改完之后仍然走 5b 的验收，不采信它的输出。

**验收**：

- 用一个替身脚本当外部 agent：
  - 只在开启了的工作目录里能跑；
  - 它能读写登记的目录，同一会话里的普通 Shell 读不到；
  - `{prompt}` 不经 shell 解释；
  - 改完照常验收。
- 实机：主人在一台机器上开启 claude 或 codex，派一个小工单跑通一次。
