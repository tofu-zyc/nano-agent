# 可靠运行事件日志

`gateway/internal/eventlog` 与网页 `events.Bus` 分开。它不运行模型，也不自行授权来源；
调用方先核验真实调用及其固定权限，再提交状态和事件。只有持久提交成功的回调才能向来源确认。

## 提交和恢复

- 一个有界工作者持有 journal；`Submit` 不等磁盘、不等队列容量，受理后冻结输入。
  回调在持久化和内存发布之后、所有内部锁之外执行。停止时排空已经受理的事务。
- Job 状态与终态事件在同一条带版本、连续顺序及 SHA-256 的记录中提交并同步。
  初次创建需显式 `Admit`；普通观察不能激活不存在的任务。固定调用、创建者、silent、
  agent、执行范围和已提交结果不能被后续状态覆盖。
- 事件匹配与整份固定版本投递清单一起提交。每个投递固定
  `(event_id, hook_id, hook_revision)`，首次动作前先持久登记尝试序号。
  已结束或不确定的投递不能直接重新开始。这里采用至少一次处理；
  外部动作完成而本地回执尚未保存时，记录仍可能是 running，处理器须核实后决定，
  不能把日志幂等解释成外部副作用恰好一次。
- 新 Job 同时预留一个终态事件位置及足够的终态字节。其他事件、投递不能吃掉预留；
  容量耗尽明确拒绝新受理，来源保留 outbox，不确认后静默丢弃。
- 重放只丢弃没有换行结尾的最后半条；完整记录损坏、版本不支持、顺序错误、
  身份或索引不一致均拒绝打开，保留原文件。写入或同步结果不确定后冻结后续确认，
  重启通过已发布 journal 核实实际结果。
- 快照和 journal 使用同一个发布文件：把有效索引写入 `.next`、同步、原子替换，
  再追加后续事务。未发布副本不会被读取激活。POSIX 同步目录；
  Windows 关闭旧句柄后用 `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` 替换。

## 有界保留

默认队列 128，单事务 64 KiB，事件正文 2 KiB，Job 正文 32 KiB，
投递正文 8 KiB，最多 1024 个 Job / 2048 个事件或终态预留 / 4096 个投递 /
256 个非 Job 来源流；总有效正文加终态预留 16 MiB，journal 上限 64 MiB。
这些是同时适用的上限，字节限制可能先于数量限制生效。

已匹配且所有投递均已结束的事件可以回收正文。Job 仍保留终态身份用于去重；
当前 Job 索引达到上限会明确暂停接收新任务。非 Job 来源按固定 source_id/epoch
使用从 1 开始的序号，持久保存连续确认游标和最多 128 个乱序位置，
缺口窗口最多 4096。回收事件正文、轮转和重启后，旧序号不会再次触发动作。
不提供删除确认游标后重新接收旧来源的捷径。

silent 进入事件与固定投递记录；silent 来源不能登记可对外发声的投递。
因果深度最多 4，同一 Hook 不匹配自己直接产生的事件。规则处理器仍须继续检查
当前权限、当前 agent 和实际目标能力，这份日志不会授予权限。

## 验证

`go test -race ./internal/eventlog` 覆盖真实文件重建、半条事务、损坏保留、终态预留、
回收后去重、乱序窗口、固定规则投递、silent、队列饱和、停止排空和快照失败。
同一套测试已在原生 Windows 执行，CI 也运行原生测试。

日志模块已实现；生产 Gateway 的 Job 准入、消息确认和 Hook 处理器需接入此日志后才可
宣称相应用户路径完成。单独通过该模块测试不表示渠道或完整 Hook 已交付。
