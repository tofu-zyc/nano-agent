# 拟人 agent 自主活动重设计：调研与实施建议

## 主线闭环补全（2026-10-26，v0.8.0）

- `life` 使用同一套文件、Shell、Skill、MCP 和桌面工具，沿用 agent 工具范围；日程保存创建时的工作目录、权限上限和验收条件。访客不再获得 Agenda / Idea / Mind，也不能伪造执行调用。
- `Agenda progress` 保存检查点；`done` 必须引用本轮实际成功的操作/观察回执，先暂存，正常结束才提交。记录 `Execution.verified` 和证据；元操作、失败、明确 `effect:unverifiable` / `verified:false` 均不能验收。重复使用调用 ID 会使旧证据失效。
- 可用回执在当前模型请求正文里带 `[本轮验收凭据]`，模型复制其中的 `id`；`Agenda list` 也能查询。不能依赖兼容接口将协议里的 `tool_call_id` 元数据展示给模型。历史保留原始输出，旧轮次和重复 ID 的旧回执不会被重新标记。
- 内心活动不广播过程，审批单仍送回创建日程的管理员窗口，管理员能在那里批准。取消、挪动、手动完成的决定不会被迟到结果覆盖。
- 定时任务有效结果、相关设备上下线接入外部事件；事件合并并提前检查。最近的认识和反思中的下一步调整会进入下一次决策说明。
- 网页显示完成条件、检查点、已验收 / 待验收 / 未完成及证据原文。
- `scripts/e2e-autonomy.py` 用真网关、真 C 内核/执行器验证审批写入、检查点、网关重启续做、真实回读验收及越界失败。模型是本机确定性替身，不使用真实渠道或密钥；已在开发机和 linux-pc 通过。
- `scripts/e2e-autonomy-real.py` 在 linux-pc 使用已配置的真实 `deepseek-v4.1-flash` 完成两轮文件任务：自己创建日程、读取不知道的随机文本、审批写入、存检查点、重启后继续、回读最终文件并关联证据验收。测试端核对内容与第一轮文件修改时间；两轮共 49,256 个模型 token（包含缓存输入），不是跨多日评估。加密端点和密钥的临时副本在结束时删除。

长期行为自然度、真实模型对更多业务验收条件的理解仍需实际使用评估；工具回执只能证明操作与观察，不能替代任意业务目标的语义判断。

日期：2026-10-26。状态：v0.7.3 已实现第一版（2026-10-26）：核心闭环、持久化、工具、UI 和测试完成；长期行为体验评估还没做。

建议在现有 Go Gateway 中加入事件驱动的自主活动控制层，采用 BDI 的目标与意图管理，借鉴 Generative Agents 的记忆、反思、日程与重规划。保留当前模型、内核和工具执行链路。空闲时间成为可选触发器，agent 自己的约定、计划和新发现也能驱动下一步。

这里的“心智模型”指可持久化、可更新的自我描述、对环境的认识、目标、承诺和当前进展。它应能解释行为为何连续，不能仅是一段每轮重新生成的内心独白。

## 1. 当前实现：以代码为依据

| 代码位置 | 实际行为 | 对需求的影响 |
| --- | --- | --- |
| `gateway/internal/app/life.go`：`lifeBlocked`、`lifeQuiet` | 最近 20 分钟有人找过 agent，就阻止普通自主唤醒 | 持续聊天会推迟 agent 自己的活动，甚至一直不执行 |
| 同文件：`lifeLevels`、`lifeInterval` | low 为 2–4 小时，normal 为 1–2 小时，high 为 30–60 分钟；区间内随机，长时间没人找时减半 | 触发主要由活跃档位决定，未表达目标的紧迫性和自己的约定 |
| 同文件：`lifeState` | 保存下次唤醒、每日计数、token 用量、最近活动摘要、待回复对象和 FollowUp | 缺少结构化的持续目标、意图、执行游标、可重排日程 |
| 同文件：`lifeHeard` | 把事件追加到内心会话，等待下次唤醒读取 | 有记录事件的入口，但事件本身不能要求及时处理 |
| 同文件：`followUpTick` | 在普通自主唤醒判断前处理预约回访 | 已有部分按时间主动触发的基础；“所有自主行为必须空闲”并不完全准确 |
| `gateway/internal/app/context.go`：`contextParts` | life 内部会话提供搜索、Knowledge、Message；没有 Schedule、通用文件工具或 MCP | 仅修改提示词无法获得自主排期或桌面操作能力 |
| `gateway/internal/app/schedules.go` | 已有持久化任务、触发、运行、结果记录等执行机制 | 可复用执行设施，但定时任务列表并不是 agent 的完整日程和目标模型 |
| `gateway/internal/app/dream.go`、`memory.go` | 已有按 agent 分开的记忆、日记来源、检索和后台整理 | 保留这些资产，让反思结果能够更新目标与认知状态 |
| `gateway/internal/app/doing.go`：`agentDoing` | 由正在执行的会话、作息和距上次活动时间推算“在干嘛” | UI 状态不能作为真实活动和意图的唯一来源 |

因此，不建议只缩短 20 分钟、调高活跃度、增加随机唤醒，或让模型每分钟生成一段“想法”。这些改动不能建立跨轮次的目标连续性。

## 2. 值得采用的已有方案

“成熟”需要区分长期存在的控制架构、实际产品组件和研究原型。以下方案没有任何一个已经替本项目完成“拟人伙伴 + 自主日程 + 桌面执行”的整套集成；这里给出的是可核对的机制及其适用范围。

| 方案 | 可以借鉴什么 | 成熟度与边界 | 在本项目中的用法 |
| --- | --- | --- | --- |
| [Jason / BDI](https://github.com/jason-lang/jason/blob/main/doc/tutorials/hello-bdi/readme.adoc) | Beliefs（认知）、Desires（愿望）、Intentions（已承诺目标）；对事件反应、挂起、恢复、放弃意图 | 已有完整语言与运行时的传统 agent 架构；不是开箱即用的 LLM 拟人产品 | 作为控制层的语义骨架，在 Go 中实现必要部分，无需引入 Java 运行时 |
| [Generative Agents](https://arxiv.org/abs/2304.03442) | 记忆流、检索、反思、日计划、行动拆分、对观察事件重规划 | 有论文与开源实现的研究原型，主要验证模拟环境中的可信行为；不能据此宣称真实桌面任务可靠 | 用来设计连续的生活计划、兴趣与记忆之间的关系 |
| [Letta 的记忆与 dreaming](https://docs.letta.com/configuration/memory) | 跨会话持久记忆，后台整理；当前官方文档支持按完成步骤数或上下文压缩触发 dreaming | 产品化的持久 agent / 记忆能力；没有单凭这项机制就解决自主目标与日程 | 借鉴事件触发的记忆维护和前后台分工，复用本项目已有 memory / dream |
| [Concordia](https://github.com/google-deepmind/concordia) | 把记忆、观察、指令和行动选择组织为组件，执行由引擎协调 | 面向生成式社会模拟的框架；Game Master 对模拟行为的判定不能替代真实工具回执 | 借鉴模块化的状态与决策输入，避免把所有内容塞进一个长提示词 |
| [Humanoid Agents](https://github.com/HumanoidAgents/HumanoidAgents) | 基本需求、情绪、关系状态影响后续计划 | 研究型模拟平台；饥饿等具身状态不直接适用于软件 agent | 可选借鉴好奇、熟悉度、注意力等行为变量；不必伪造身体生活 |
| [MaiBot / Maisaka 主动任务接口](https://github.com/Mai-with-u/maibot-plugin-sdk/blob/main/docs/guide.md#maisaka----上下文与主动任务) | 将主动任务意图交给既有聊天流处理，而不是直接发送预先写好的提醒 | 现有拟人聊天工程的参考；本次核对的是官方 SDK 接口说明，未完整审计其运行时 | 借鉴事件进入统一对话执行链的方式；不把插件 API 等同于完整心智模型 |

Generative Agents 另核对了实现：[plan.py](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/cognitive_modules/plan.py) 在新一天规划日程、行动结束后选择下一步，并响应检索到的事件；[reflect.py](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/cognitive_modules/reflect.py) 包含按累计重要性触发反思和保存证据引用的逻辑。建议借鉴机制，按本项目的真实执行环境重写控制层。

推荐组合：**BDI 管理承诺与生命周期，Generative Agents 提供规划和反思方法，既有 memory / dream 保存长期经验，Gateway 负责调度和真实执行。** 这是结合本项目代码后的设计判断，并非上述项目现成提供的组合。

## 3. 持久状态模型

按 agent 保存一份自主状态，所有聊天共享；每个聊天继续保留自己的上下文。不要为每个聊天复制出一套独立人格目标。

| 状态 | 主要内容 | 更新方式 |
| --- | --- | --- |
| Self | 价值偏好、长期兴趣、能力、自主活动范围 | 人格配置为稳定基线；允许的偏好更新有来源和版本，不能改写权限 |
| Beliefs | 对当前环境、用户约定、任务状况的认识 | 保存来源、时间、置信度；区分观察事实、他人陈述和自己的推测 |
| Desires / Ideas | 想研究的问题、想尝试的事情、未完成的兴趣 | 可以积累、合并、过期、放弃；尚未成为执行承诺 |
| Intentions | 当前决定推进的少量目标 | 记录原因、优先级、完成条件、所需能力、预算、下一步和阻塞条件 |
| Agenda | 今日计划、固定约定、可挪动时间块 | 使用时间窗口、预计时长、依赖和可中断性；允许重排 |
| Execution | 本次行动与结果 | 保存实际 run / tool 关联、游标、成功或失败证据；用于恢复与防重 |
| Reflection | 经验、计划偏差和下一步调整 | 更新 beliefs / ideas / intentions；不能仅写一篇独立日记 |

建议状态带 `schema_version`、`revision`；事件带 `id`、`agent_id`、`kind`、`source`、`occurred_at`、`dedupe_key`、关联会话和计划 ID。以上是建议字段，不是已存在的接口。

长期记忆用于保存经历和稳定信息，心智状态用于表达“现在相信什么、决定推进什么”。二者通过来源引用连接，避免重复存储整段聊天。

## 4. 事件驱动的工作循环

```text
聊天中产生的约定 / 工具结果 / 外部变化 / 日程到点 / 自己设定的复查时间
                                  ↓
                     持久事件队列、合并与去重
                                  ↓
                  读取心智状态和相关记忆，判断是否需要决策
                                  ↓
                  维持计划 / 调整计划 / 执行一步 / 等待
                                  ↓
                    现有 Gateway → kernel → 工具
                                  ↓
                    实际结果 → 状态更新 → 下次触发
```

普通时钟扫描只检查到期事件，不要求每次扫描都调用模型。无事件时可以等待；有长期兴趣时由 agent 选择下次复查时间。保留低频兜底扫描，处理漏掉的定时器和进程重启。

建议事件包括：`conversation_updated`、`commitment_created`、`agenda_due`、`action_completed`、`action_failed`、`external_changed`、`reflection_due`、`self_check_due`、`manual_wake`。高频聊天事件先合并，避免每句话再启动一次完整规划。

决策输出应为受校验的结构：消费哪些事件、更新哪些状态、选择哪个 intention、执行或等待、下次复查时间和简短理由。允许明确输出“现在不做任何事”。不要要求模型持续流式生成内心独白，也不要把模型自述的完成状态直接写成真实执行结果。

### 移除不合适的全局空闲门槛

把“是否可以内部处理”“是否可以占用某项资源”“是否适合主动打扰用户”分开判断。

- 最近有人联系过，不再统一阻止日程到点、结果回调和重要约定处理。
- 用户聊天优先获得交互资源；自主行动可在安全边界挂起，保留下一步，而不是丢弃意图。
- 夜间安静、联系频率、对方尚未回复等规则用于主动发消息。普通探索可以受 agent 作息约束；明确约定的任务遵守自己的时间要求。
- 每个 agent 的心智状态变更串行提交；模型请求在锁外运行，提交时校验 revision，避免过期规划覆盖刚收到的新约定。
- 桌面、浏览器会话等资源另有占用协调；agent 可以继续规划，不代表可以并发操作同一桌面。

## 5. 自己规划日程

在新一天、重要约定变化或明显偏离原计划时生成或修订日程。不要反复重做整天计划。

日程项至少区分：用户明确约定、agent 已承诺的目标、自选探索。固定约定有时间和优先级；探索有可移动时间窗口，允许延期或取消。一个目标可以跨天延续，不能到第二天自动遗忘。

例子：上午决定下午查阅一个感兴趣的话题，预留 20 分钟；途中用户要求处理问题，暂停探索；对话完成后检查剩余时间并继续。此前约好 16:00 复查的任务仍会在到点时进入调度，不需要再等待 20 分钟没人说话。

复用 `internal/schedule` 与 `app/schedules.go` 中适合的时间计算、持久任务和执行能力，新增 agenda 层负责语义关系。不要把每个念头都变成独立 cron，也不要让 Schedule 和 Agenda 同时拥有同一项工作的触发权。

首次接入可只提供少量操作：查询日程、建立或调整计划项、取消计划、报告执行结果。工具名与 schema 由实施者结合现有工具风格确定。涉及真实工具的行动仍通过已有权限和执行链；自主计划本身不自动扩大权限。

agent 的个人日程默认存在本项目中。接入用户外部日历属于后续能力，不把 agent 的兴趣活动默认写进用户日历。

## 6. 突发奇想的形成与筛选

想法来自最近观察、未解决的问题、长期兴趣和已有目标之间的新联系。情境决定候选内容；适量随机性只影响探索时机或近似候选的选择。

建议流程：

1. 有新信息或到自选探索时间时，生成少量候选，并写明关联记忆或事件。
2. 对重复、刚尝试失败且条件未变、超过自主范围、与当前承诺冲突的候选过滤或延期。
3. 按兴趣关联、信息增益、预计成本、时效和当前负荷选择；允许一个都不选。
4. 选中后转为 intention，再放入可挪动日程；只有进入执行阶段才调用真实工具。
5. 将结果反馈给兴趣和计划：学到了什么、是否还值得继续、何时再看。

例如，agent 看到一个与近期话题相关的资料，形成“想比较两种解释”的想法，决定花十分钟阅读并记笔记。它可以做完后等自然聊天时提起，也可以认为值得立即分享；“产生想法”“执行想法”“主动联系用户”是三次不同的决定。

可增加 curiosity、novelty、social 等行为参数，但第一阶段不必引入复杂情绪数值系统。状态应服务于可解释的选择，不能成为“每天必须假装吃饭、出门”的脚本。

## 7. 执行可靠性与恢复

- 将意图的生命周期明确为候选、已接纳、执行中、等待、暂停、完成、失败或取消。成功需要工具结果或可核实的产物。
- 事件至少一次投递，消费去重；计划步骤有稳定 ID。进程中断后先恢复“进行到哪里”，再决定重试。
- 对外部操作结果未知时，重新观察状态，不无条件重放点击、发送或创建动作。严格的跨系统 exactly-once 不应作为默认承诺。
- 单独计量规划、执行、反思的调用成本。预算耗尽后保存等待原因和恢复时间，不能把循环错误记成正常休息。
- 对话回合、内心回合、dream 和计划回调都需要明确的 agent 身份。实现前先完成会话归属修复，或至少建立一致的身份解析入口。

| `app/doing.go`、Web agent 面板 | 读取真实执行状态，展示当前计划、下次安排、想法清单和简短行动原因 |

UI 建议先提供“在做什么”“今天的安排”“想到的事情”“最近完成的事”，以及暂停自主活动、取消计划和立即唤醒。显示可检查的计划和结果摘要，无需展示原始模型推理。

与 computer use 的关系：Cua Driver 是执行能力，由既有 MCP 层提供；它不负责目标和日程。第一版自主循环可先用搜索、知识和普通任务验证，桌面能力在接入完成后加入。参见 `docs/PLAN-computer-use.md`。

## 9. 分阶段交付

1. **身份与状态基础**：完成会话切换方案；引入版本化心智状态、事件队列、意图生命周期，能够恢复到下一步。
2. **主动计划闭环**：聊天约定、日程到点和执行结果可触发；agent 可排期、调整、取消和续做；取消全局 20 分钟空闲依赖。
3. **反思与探索**：把经验连到未来行为，加入带来源的想法池、筛选和探索额度。
4. **体验与能力扩展**：日程和状态 UI、跨设备能力、桌面资源协调；依据实际使用评估行为自然度。

第一阶段建议采用少量明确状态和一份紧凑的决策上下文。待需要时再扩展复杂关系模型、多层情绪或更细粒度的执行并行。

迁移时保留旧 `life.json` 的近期活动、待回复和 FollowUp；把旧 Next 转成可解释的下一次复查。保留旧配置兼容入口，记录迁移版本，重启不能再次重复导入。旧 FollowUp 与新 Agenda 只保留一个实际执行者。

## 10. 验收场景

使用可控时间、固定随机种子和模拟模型/工具，先验证控制逻辑，再做真实模型体验评估。

- 持续有聊天时，明确约定的复查仍准时进入队列；没有额外 20 分钟门槛。
- 同一条事件重复到达，不会重复创建目标或重复执行步骤。
- 用户打断后，自主计划可暂停并从检查点续做；新约定不会被旧规划覆盖。
- agent 能自己安排、挪动、取消计划，跨日和时区变化后语义仍正确。
- 进程重启、到期错过、工具超时、桌面离线都有可检查状态；不虚构活动已完成。
- 突发想法有情境来源、能去重，也允许不执行；不会因无新信息无限循环调用模型。
- 内部活动与联系用户分开限额；未被回复时不连续骚扰同一对象。
- 多会话共享同一 agent 的目标；不同 agent 的人格、记忆、日程与回调不会串用。
- 每次行动可追溯至事件、意图、实际结果；能统计计划完成、延期、过期、打断恢复和模型开销。

上述均为后续实现的验收要求，本次未实施或宣称通过。

## 实施结果（v0.7.3，2026-10-26）

**新增模块**

- `gateway/internal/autonomy`：版本化心智状态（`schema_version` / `revision` / `seq`）、事件去重与消费、BDI 意图生命周期、议程、想法池、执行记录、反思、每日预算、重启恢复、`Retry` / `RecordSkipped`。纯规则选择（`Due` / `Next` / `CanStart`），不把“空闲 20 分钟”写进控制层。
- `gateway/internal/app/autonomy.go`：事件来源（聊天合并 10 分钟、FollowUp、dream 反思、日程到点、外部结果、主人叫醒）；每个 agent 一次只启动一件事；约定优先于探索；约定不受作息限制；探索遵守作息和每日次数；资源占用单独判断（内心会话在跑就延后，不丢意图）；预算按天；暂停会打断正在跑的一轮并保留下一步；重启时不重放未知执行。
- `gateway/internal/app/autonomy_tools.go`：`Agenda`（list/add/move/cancel/done）和 `Idea`（list/add/schedule/drop/defer）。想法必须有来源；`done` 必须写真实结果；只有“真的调用了工具 + 正常结束”才把日程标成完成，否则往后挪。旧 `FollowUp` 继续作为聊天回访的执行者，没有复制成 Agenda，保证同一件事只有一个执行者。
- UI / 命令 / API：agent 节点新增「自主活动」卡（日程、目标、想法、最近做完、暂停/恢复/叫醒）；`GET/POST /api/agents/{id}/autonomy`；`/autonomy [pause|resume|wake]`。
- 与现有资产的关系：人格/守则由 `agents/<id>/persona.md`、`life.md`、`skills/life/SKILL.md` 提供；长期记忆仍由 memory / dream 保存；日程到点复用 `@<agent>/life` 的内心会话和现有模型/工具链。

**与方案的差异和理由**

- 第一版不引入数值情绪/关系状态，也不伪造“吃饭、出门”等具身活动；用兴趣、新颖度、成本三个可解释参数筛选想法。
- 不把每条事件都立刻唤醒模型：聊天事件 10 分钟内合并，只把下次检查提前；没有到期事件时不调用模型。
- 没有实现外部日历，也不把 agent 的日程默认写进用户日历。
- 反思来自 dream 整理、`Agenda done` 的真实结果和 v0.7.4 的 `Mind` 工具；`Mind` 可以更新长期兴趣、认识（信念）和反思，但不会自动改人格文件，自我/价值偏好仍以人格文件为基线。
- 时间粒度到分钟；睡眠窗口内只执行明确约定；跨日由日期滚动和持久化的时间戳处理。

**验证**

- `internal/autonomy` 单元测试：事件去重、优先级、约定跨作息、预算、重启不重放、想法来源/排期/推迟/放弃、`Finish` 必须真实工具结果、时间解析。
- app 集成测试（模拟时间 + 假模型/假内核，走真实模型请求和工具执行链）：到点约定在刚聊天后仍执行；没有工具不虚报完成；暂停/恢复；预算阻断与恢复；重启恢复；聊天事件合并不每条唤醒；想法必须有来源并变成可挪动的探索时间。
- UI：`check-web-ui.py` 新增自主活动卡和接口检查，0 failures。

**剩余问题**

- 真实使用中的“日程是否自然、反思是否真的改变长期选择”需要长期体验评估，不能只凭测试宣称。
- 多 agent 共享同一桌面的资源协调见 `PLAN-computer-use.md`（目前同一台桌面的工具调用串行）。
- 旧 `life.json` 在大量近况/回访数据下的迁移性能没有专门压测。
