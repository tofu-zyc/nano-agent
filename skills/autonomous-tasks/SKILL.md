# 安排、执行和续做任务

这项能力使用 nano-agent 的 Agenda，不是外部日历。计划沿用创建时的工作目录和权限，审批仍由管理员处理；不能把一项任务同时放进 Agenda 和 Schedule 让它重复执行。

## 先判断用什么

- 当前立刻能完成的普通任务直接执行，不为一次操作硬建日程。
- 明确约定稍后做、agent 自己决定继续推进、需要跨轮次检查点时用 Agenda。
- 固定时间反复运行、结果投递到指定窗口时，加载 `scheduled-tasks` 用 Schedule。
- 只有拟人型 agent 的管理员上下文提供 Agenda。缺工具时用 Gateway 查询当前 agent、工作目录和权限；不要猜工具、改成放行模式或擅自把所有 agent 改为拟人型。旧网关没有 progress/evidence 参数时，说明当前能力缺口，不能假装已支持检查点验收。

## 排期

先 `Agenda {"action":"list"}` 看已有安排；同一个用户约定复用原项，避免重复建。确认任务要在哪台机器、哪个已挂载目录执行，以及怎样检查结果。已有上下文足够就直接用；只问真正缺少的时间或范围。

```json
{"action":"add","title":"整理工作目录里的报告","kind":"commitment","when":"+30m","note":"读取草稿，整理后保存为 final.md；不要改原始数据。","criteria":"final.md 存在且包含要求的三部分；保存后重新 Read 核对内容。"}
```

- `commitment` 是与用户的约定；`plan` 是自己决定的工作；`checkup` 是复查；`exploration` 是可挪的探索。
- `when` 用网关当前时区，支持 `15:30`、`明天 09:00`、完整日期时间和 `+30m`。以当前系统消息的时间为准，不写死时区或沿用旧示例日期。
- `note` 写到时需要知道的操作、限制、目标路径；`criteria` 写完成结果和检查方法。日程运行不等于把整段原聊天重新发给模型。
- 工作目录或权限需要修改时走现有网关审批。创建完简短告知具体时间和目标，不把“安排好了”当成“做完了”。

## 到点执行 / 从检查点继续

1. 读取当前日程 ID、完成条件和上次检查点。先观察已有文件/窗口/外部状态，确认哪些步骤已经完成，哪些结果未知。
2. 用当前工具推进一段实际工作。桌面任务先加载 `computer-use`；只写计划、查询 Agenda/Idea/Mind 不算执行。
3. 长任务在完成一段可观察工作后用 progress 保存检查点，写清产物、已核对结果、下一步和不能重放的未知操作：

```json
{"action":"progress","id":"ag-实际ID","checkpoint":"first.md 已保存并回读一致；下一步补第二部分，再生成 final.md。上次点击提交后连接断开，状态未知，必须先查询，不能重发。"}
```

4. 目标机器离线、目录被删、审批未通过或资源占用时保留检查点，按原因等条件恢复或 move 改期；不能换到 HOME / 别的电脑做出同名文件冒充完成，也不循环安装或重试同一错误。

## 核验并提交完成

先按 criteria **重新观察结果**。保存文件后回读；桌面操作后读实际控件/状态或应用产物；外部提交要核对服务返回和实际状态。工具调用返回成功不能替代业务结果。

有效的本轮工具结果在模型请求中带：

```text
[本轮验收凭据] {"id":"实际工具回执ID","tool":"Read"}
```

把其中实际 `id` 原样放进 `Agenda done` 的 `evidence` 数组，`note` 说明怎样满足条件。找不到时用 Agenda list 查本轮可用凭据；不要猜 ID、填工具名、填结果描述或引用上轮 ID。

```json
{"action":"done","id":"ag-实际ID","note":"已生成 final.md，并重新读取确认三部分完整、内容符合要求。","evidence":["从本轮核验结果复制的实际id"]}
```

失败回执、明确未确认效果的 MCP 回执和元操作不能当凭据；若另一次真实观察确认结果，则引用那次观察。验收先暂存，只有本轮正常结束才会提交完成；中断、超时或轮数耗尽都不算完成。

需要挪动/取消时分别用 `move` / `cancel` 和查到的原 ID。不要为了让状态变绿而更改完成条件或绕过审批。
